소프트웨어 보안을 처음 다루기 전에 먼저 소프트웨어 실패가 얼마나 큰 문제인지 볼 필요가 있다. 보안이라고 하면 보통 해킹이나 공격 방어만 떠올리기 쉬운데, 실제로는 소프트웨어 자체의 품질 문제나 버그도 큰 보안 문제로 이어질 수 있다.

![](../images/Pasted%20image%2020260603205247.png)

여기서 poor software quality로 인한 미국의 비용이 약 2.08조 달러로 나오는데, 이 규모가 한국 GDP나 이탈리아 GDP보다 크다. 즉, 소프트웨어 오류는 단순히 프로그램이 조금 잘못 동작하는 수준이 아니라, 국가 경제 규모와 비교될 정도로 큰 손실을 만들 수 있다는 의미다.

#### Emphasize software assurance
그래서 소프트웨어 보안에서는 문제가 터진 뒤에 대응하는 것보다, 개발 과정에서부터 실패 가능성을 줄이는 것이 중요하다. 이를 software assurance라고 볼 수 있다. 테스트, 코드 리뷰, 품질 보증 같은 과정을 개발 생명주기 전체에서 계속 수행하면서 소프트웨어가 의도한 대로 동작하는지 확인해야 한다.
#### Implement robust security measures
또한 보안 기능도 처음부터 고려해야 한다. 안전한 코딩 규칙을 지키고, 주기적으로 보안 점검을 하고, 인증이나 암호화 같은 기본적인 보안 메커니즘을 제대로 적용해야 한다. 단순히 기능 구현이 끝난 뒤에 보안을 덧붙이는 방식이면 취약점이 남기 쉽다.
#### Utilize reliable security systems
외부 공격을 막기 위한 보안 시스템도 필요하다. 방화벽, 침입 탐지 시스템, 안티바이러스 같은 도구는 외부 공격이나 악성코드로부터 시스템을 보호하는 역할을 한다. 하지만 이런 도구만으로는 부족하기 때문에 정적 분석, 동적 분석, 취약점 스캐너, 침투 테스트 같은 분석 도구를 사용해서 코드나 시스템 내부의 약점도 찾아야 한다.
#### Foster continuous monitoring
운영 중에는 지속적인 모니터링이 필요하다. 실제 서비스 환경에서는 예상하지 못한 입력이나 공격 시도, 비정상적인 트래픽이 발생할 수 있기 때문에 로그를 남기고 이상 징후를 빠르게 감지해야 한다. 그리고 이미 알려진 취약점은 패치를 통해 해결해야 하므로, 소프트웨어를 최신 안정 버전으로 유지하는 것도 중요하다.
#### Regularly update and patch software
마지막으로 사람의 역할도 크다. 개발자나 운영자가 보안 위험을 인식하지 못하면 좋은 도구가 있어도 문제가 생길 수 있다. 그래서 보안 교육을 통해 책임감을 갖도록 하고, 개발자·운영자·보안 담당자 사이의 협업과 소통을 통해 위험을 초기에 발견하는 것이 중요하다.

정리하면, 소프트웨어 보안은 단순히 공격을 막는 기술만을 의미하지 않는다. 소프트웨어 실패가 큰 비용으로 이어질 수 있기 때문에, 개발 단계에서는 품질을 높이고, 구현 단계에서는 안전한 코드를 작성하고, 운영 단계에서는 모니터링과 패치를 계속 수행해야 한다는 흐름으로 이해하면 된다.

# Software Assurance

## Software bug
앞에서 소프트웨어 실패가 비용적으로 얼마나 큰 문제인지 봤기 때문에, 이제는 그 실패가 구체적으로 어디서 시작되는지를 봐야 한다. 그 출발점이 바로 **software bug**다. 즉, 보안 문제를 이해하려면 먼저 버그가 단순한 실수가 아니라 시스템의 잘못된 동작을 만들어내는 원인이라는 점을 잡아야 한다.

Software bug는 프로그램이나 시스템 안에 있는 error, flaw, fault를 의미한다. 쉽게 말하면 코드나 설계 안에 들어 있는 잘못된 부분이다. 이 버그 때문에 소프트웨어가 예상과 다른 결과를 내거나, 의도하지 않은 방식으로 동작하게 된다.

중요한 점은 모든 버그가 같은 수준의 문제는 아니라는 것이다. 어떤 버그는 화면 출력이 조금 이상한 정도로 끝날 수 있지만, 어떤 버그는 시스템 중단, 데이터 손상, 권한 탈취, 대규모 장애 같은 심각한 문제로 이어질 수 있다. 그래서 앞에서 말한 것처럼 소프트웨어 품질 실패의 비용이 커지는 것이다.

## Kinds of software bugs

버그의 종류는 크게 몇 가지로 나눠볼 수 있다.

먼저 **arithmetic bug**는 계산 과정에서 생기는 오류다. 대표적으로 division by zero가 있다. 0으로 나누는 연산은 정의되지 않기 때문에 프로그램이 중단되거나 예외가 발생할 수 있다. 또 floating point 연산을 사용할 때 numerically unstable algorithm이 문제가 될 수 있다. 실수 연산은 컴퓨터 내부에서 정확히 표현되지 않는 경우가 많기 때문에, 작은 오차가 반복되면서 결과가 크게 틀어질 수 있다.

다음은 **logic bug**다. 이건 프로그램의 흐름이나 조건이 잘못된 경우다. 예를 들어 종료 조건을 잘못 작성하면 infinite loop가 발생할 수 있고, 재귀 함수의 base case가 잘못되면 infinite recursion이 발생할 수 있다. 이런 경우 프로그램이 끝나지 않거나, 스택이 계속 쌓여서 결국 비정상 종료될 수 있다.

**Resource bug**는 메모리나 파일, 네트워크 연결 같은 자원을 잘못 다루는 문제다. 대표적인 예가 buffer overflow다. 정해진 버퍼 크기를 넘어 데이터를 쓰면 다른 메모리 영역을 침범하게 되고, 이게 보안 취약점으로 이어질 수 있다. 공격자가 이를 이용하면 프로그램 흐름을 조작하거나 악성 코드를 실행하게 만들 수도 있다. double free error도 중요한데, 이미 해제한 메모리를 다시 해제하는 문제다. 이 역시 메모리 손상이나 취약점으로 연결될 수 있다.

마지막으로 **interface bug**는 API나 외부 기능을 잘못 사용하는 경우다. 함수의 사용법을 잘못 이해하거나, 입력 조건을 지키지 않거나, 반환값을 제대로 확인하지 않으면 문제가 생길 수 있다. 예를 들어 어떤 API가 실패할 수 있는데도 실패 여부를 확인하지 않고 다음 로직을 실행하면 예상치 못한 오류가 발생할 수 있다.

# Code Review
앞에서 버그의 종류를 봤다면, 이제는 그런 버그를 개발 과정에서 어떻게 줄일 수 있는지로 넘어간다. 그중 가장 기본적인 방법이 **Code Review**이고, 여기서는 코드 리뷰를 할 때 중요한 기준으로 **Clean Code**를 다룬다.

Clean Code는 단순히 코드가 예쁘게 정리되어 있다는 뜻이 아니다. 핵심은 **다른 사람이 봐도 쉽게 이해할 수 있고, 수정하거나 확장하기 쉬운 코드**라는 것이다. 코드가 복잡하고 의도가 잘 드러나지 않으면 버그를 찾기도 어렵고, 기능을 수정할 때 새로운 버그가 생길 가능성도 커진다. 그래서 소프트웨어 보안이나 품질 관점에서도 읽기 쉬운 코드는 중요하다.
### Naming
먼저 **Naming**이 중요하다. 변수명, 함수명, 클래스명이 의미 있게 작성되어 있어야 한다. 예를 들어 `a`, `temp`, `data`처럼 너무 추상적인 이름만 쓰면 나중에 코드를 읽을 때 이 값이 무엇을 의미하는지 바로 알기 어렵다. 반대로 `userCount`, `encryptedPassword`, `validateToken`처럼 이름만 봐도 역할이 드러나면 코드의 흐름을 이해하기 쉬워진다.
### Function
다음은 **Function은 하나의 일만 해야 한다**는 것이다. 함수 하나가 입력 검증, DB 저장, 로그 출력, 예외 처리, 응답 생성까지 모두 담당하면 코드가 길어지고 복잡해진다. 그러면 어디서 문제가 생겼는지 찾기도 어렵다. 그래서 함수는 가능한 한 하나의 책임만 가지도록 나누는 것이 좋다.

여기서 연결되는 개념이 **Single Responsibility Principle**이다. 하나의 함수나 모듈, 클래스는 하나의 책임을 가져야 한다는 원칙이다. 책임이 분리되어 있으면 특정 기능을 수정할 때 영향 범위가 줄어든다. 예를 들어 인증 로직과 결제 로직이 섞여 있으면 인증 부분을 고치다가 결제 기능에 문제가 생길 수 있다. 반대로 역할이 잘 나뉘어 있으면 수정과 테스트가 쉬워진다.
### Code Refactoring
**Code Refactoring**은 코드의 외부 동작은 그대로 유지하면서 내부 구조를 개선하는 과정이다. 기능은 똑같이 동작하지만, 중복 코드를 줄이고, 함수 이름을 명확하게 바꾸고, 너무 긴 함수를 나누는 식으로 코드 품질을 높인다. 리팩토링을 하는 이유는 당장 보이는 기능 추가보다, 이후 유지보수와 버그 예방에 도움이 되기 때문이다.
### TDD
마지막으로 **TDD**, 즉 Test-Driven Development가 나온다. TDD는 코드를 먼저 작성하는 것이 아니라, 테스트를 먼저 작성하고 그 테스트를 통과하도록 코드를 구현하는 방식이다. 이렇게 하면 개발자가 “이 기능이 어떤 조건에서 어떻게 동작해야 하는지”를 먼저 생각하게 된다. 그래서 요구사항이 더 명확해지고, 나중에 코드를 수정해도 기존 기능이 깨졌는지 테스트를 통해 바로 확인할 수 있다.

# Testing
앞에서 코드 리뷰를 통해 버그를 줄이는 방법을 봤다면, 이제는 실제로 프로그램이 요구사항대로 동작하는지 확인하는 단계로 넘어간다. 코드가 깔끔해 보여도 실제 실행 결과가 틀릴 수 있기 때문에, **Testing**은 소프트웨어가 “정말 의도한 대로 동작하는지” 확인하는 과정이라고 보면 된다.

## Software Testing
Software Testing은 소프트웨어 제품이나 애플리케이션이 해야 할 일을 제대로 수행하는지 평가하고 검증하는 과정이다. 단순히 실행해보는 것이 아니라, 요구사항에 맞는 입력을 넣었을 때 기대한 출력이 나오는지 확인하는 것이다. 그래서 테스트를 잘하면 버그를 미리 발견할 수 있고, 나중에 장애가 발생한 뒤 수정하는 비용을 줄일 수 있으며, 성능 문제도 함께 확인할 수 있다.

![](../images/Pasted%20image%2020260603210315.png)

그림에서 흐름을 보면 먼저 **Problem**이 있고, 이 문제를 해결하기 위해 요구사항과 설계가 만들어진다. 즉, `Design ⊢ Req`는 설계가 요구사항을 만족해야 한다는 의미로 볼 수 있다. 그다음 설계를 바탕으로 실제 **Program**을 구현하고, 요구사항과 설계를 바탕으로 **Test case**를 만든다. 테스트 케이스는 단순한 입력 하나가 아니라, “어떤 입력을 넣었을 때 어떤 출력이 나와야 하는가”까지 포함한다.

결국 테스트의 핵심은 Program이 Test case를 만족하는지 확인하는 것이다. 프로그램이 설계를 구현했고, 테스트 케이스가 요구사항을 잘 반영하고 있다면, 테스트를 통과한다는 것은 프로그램이 요구사항에 맞게 동작할 가능성이 높다는 의미가 된다. 물론 모든 경우를 테스트할 수는 없기 때문에, 어떤 테스트 입력을 선택하느냐가 매우 중요하다.

## Testing Approach

테스트 방식은 크게 **white-box testing**과 **black-box testing**으로 나눌 수 있다.

### White-box testing
White-box testing은 프로그램 내부 구조를 알고 테스트하는 방식이다. 코드의 조건문, 반복문, 분기 구조 같은 control structure를 보고 테스트 케이스를 만든다. 예를 들어 if문이 있으면 true일 때와 false일 때를 모두 확인하고, 반복문이 있으면 0번 실행, 1번 실행, 여러 번 실행되는 경우를 나눠서 볼 수 있다. 내부를 보고 테스트하기 때문에 코드 경로를 꼼꼼히 확인할 수 있다는 장점이 있다.

### Black-box testing
Black-box testing은 내부 코드를 보지 않고, 입력과 출력만 보고 테스트하는 방식이다. 프로그램을 하나의 검은 상자처럼 보고, 요구사항에 따라 어떤 입력을 넣으면 어떤 결과가 나와야 하는지만 확인한다. 예를 들어 로그인 기능이라면 내부 구현 방식은 몰라도, 올바른 아이디와 비밀번호를 넣었을 때 로그인 성공, 틀린 값을 넣었을 때 로그인 실패가 나오는지를 확인하는 식이다.

즉, white-box는 **코드 구조 중심**, black-box는 **기능 요구사항 중심**이라고 정리할 수 있다. 둘 중 하나만 쓰는 것이 아니라, 실제로는 둘을 함께 사용해야 한다. 내부 코드 경로도 확인해야 하고, 사용자 관점에서 기능이 제대로 동작하는지도 확인해야 하기 때문이다.

## The Importance of Testing Inputs

마지막 예제는 테스트 입력을 잘 고르는 것이 왜 중요한지를 보여준다.

![](../images/Pasted%20image%2020260603210425.png)

`numZero` 함수는 배열 안에 있는 0의 개수를 세는 함수다. 요구사항을 보면 배열이 null이면 예외를 던지고, 그렇지 않으면 배열 안에 있는 0의 개수를 반환해야 한다. 그런데 코드에서는 반복문이 `i = 1`부터 시작한다. 원래 배열의 첫 번째 원소부터 검사해야 하므로 `i = 0`부터 시작해야 하는데, 여기서 fault가 생긴다.

그런데 첫 번째 테스트 입력 `[2, 7, 0]`에서는 문제가 드러나지 않는다. 첫 번째 원소가 0이 아니기 때문에, 인덱스 1부터 검사해도 결과가 우연히 맞게 나온다. Expected는 1이고 Actual도 1이다. 이 경우 내부적으로는 `i = 1`부터 시작하는 error가 존재하지만, 최종 출력에는 영향을 주지 않았기 때문에 failure는 발생하지 않는다.

반면 두 번째 테스트 입력 `[0, 2, 7]`에서는 문제가 바로 드러난다. 첫 번째 원소가 0인데 반복문이 인덱스 1부터 시작하므로 이 0을 세지 못한다. 그래서 Expected는 1이지만 Actual은 0이 된다. 이때는 fault가 실행 중 error로 나타났고, 그 error가 `count` 값에 영향을 주면서 최종적으로 failure가 발생한 것이다.

여기서 중요한 구분은 이거다. **fault**는 코드 안에 있는 잘못된 부분이고, **error**는 실행 중 잘못된 내부 상태이며, **failure**는 사용자가 관찰할 수 있는 잘못된 결과다. 모든 fault가 항상 failure로 드러나는 것은 아니다. 어떤 입력에서는 숨어 있다가, 특정 입력에서만 failure로 나타날 수 있다.

# Fuzzer

앞에서 일반적인 테스트는 “정해진 입력을 넣고 기대 출력과 비교하는 방식”이었다. 그런데 실제 보안 취약점은 개발자가 예상하지 못한 이상한 입력에서 터지는 경우가 많다. 그래서 이제는 사람이 테스트 케이스를 하나하나 설계하는 방식에서 더 나아가, **무작위이거나 변형된 입력을 대량으로 넣어보면서 프로그램이 깨지는 지점을 찾는 방법**을 보게 된다. 이게 fuzzing이다.

Fuzzing의 시작은 UNIX 시스템이 비정상적으로 자주 crash되는 현상에서 출발했다. Barton Miller는 이런 crash가 네트워크 패킷에 예상치 못한 전기적 노이즈가 섞이면서 이상한 입력이 들어왔기 때문일 수 있다고 생각했다. 그래서 학생들에게 UNIX utility에 의도적으로 random input을 계속 넣어보게 했고, 실제로 많은 버그가 발견되었다. 여기서 핵심은 “정상적인 입력만 테스트하면 놓치는 문제가 있다”는 것이다.

## Ancient Fuzzers

초기의 fuzzer는 매우 단순했다. 쉼표, 세미콜론, 제어 문자 같은 것들이 섞인 긴 random text를 만들어서 UNIX command utility에 계속 넣었다. 그리고 프로그램이 crash되거나 hang이 발생하는지 관찰했다. 이런 방식만으로도 UNIX utility의 약 1/3에서 새로운 버그가 발견되었다는 점이 중요하다. 즉, 복잡한 분석 없이도 비정상 입력을 많이 넣는 것만으로 숨겨진 결함을 찾을 수 있었다.

### Shortcomings of Ancient Fuzzers
하지만 초기 fuzzer에는 한계가 있었다. 첫 번째 한계는 crash나 hang처럼 눈에 보이는 실패만 찾을 수 있다는 점이다. 프로그램이 죽지 않더라도 내부적으로 잘못된 동작을 하거나, 보안적으로 위험한 상태가 될 수 있는데 이런 silent illegal behavior는 단순 fuzzer만으로는 찾기 어렵다. 그래서 valgrind, electric fence, LLVM sanitizer 같은 dynamic analyzer를 함께 사용해서 메모리 오류나 undefined behavior를 더 잘 감지하려고 한다.

두 번째 한계는 완전히 random한 입력이 코드의 깊은 부분까지 도달하기 어렵다는 점이다. 예를 들어 JSON parser, URL parser, image decoder 같은 프로그램은 입력 형식이 어느 정도 맞아야 내부 로직까지 진행된다. 그런데 아무 문자나 무작위로 넣으면 초반 grammar check에서 바로 거부된다. 그러면 프로그램의 중요한 처리 로직까지 실행되지 못하고, 결과적으로 source code의 제한된 부분만 테스트하게 된다.

---
## Mutation-based Fuzzing
그래서 나온 방식이 **mutation-based fuzzing**이다. 완전히 무작위 입력을 만드는 것이 아니라, 먼저 정상적인 입력인 **seed**를 준비한다. 그다음 이 seed에 작은 변형을 반복해서 넣는다. 예를 들어 URL parsing library를 테스트한다면 `http://www.google.com/search?q=fuzzing` 같은 정상 URL을 seed로 두고, 일부 문자를 바꾸거나 지우거나 추가해서 살짝 이상한 URL들을 만든다.

이 방식이 효과적인 이유는 변형된 입력이 여전히 어느 정도 정상 입력의 구조를 유지하기 때문이다. 완전 random text는 parser 초반에서 바로 거부될 가능성이 높지만, 정상 URL을 조금 바꾼 입력은 내부 parsing 로직까지 들어갈 가능성이 높다. 그러다가 특정 위치의 이상한 문자나 길이, 특수문자 조합 때문에 숨겨진 버그가 드러날 수 있다.

### Mutation Operators
Mutation operator는 seed input을 어떻게 바꿀지에 대한 규칙이다. 예를 들어 random bit 하나를 뒤집거나, 연속된 byte를 바꾸거나, 일부 byte를 삭제하거나, 새로운 byte를 삽입할 수 있다. 기존 byte를 여러 번 반복하거나, dictionary에 있는 단어를 추가하거나, 연속된 byte의 순서를 섞거나, substring을 복사해서 다른 위치에 붙일 수도 있다. 여러 seed를 섞는 crossover도 가능하다.

여기서 fine-grained와 coarse-grained의 차이도 볼 수 있다. bit 하나를 flip하는 것은 매우 작은 변화라서 fine-grained mutation에 가깝다. 반면 substring을 복사해서 붙이거나 crossover를 하는 것은 입력 구조를 더 크게 바꾸는 것이므로 coarse-grained mutation에 가깝다. 작은 변화는 섬세한 오류를 찾는 데 좋고, 큰 변화는 더 새로운 실행 경로를 만들 가능성이 있다.

### Why mutation effectively disclose subtle behaviors?
Mutation이 subtle behavior를 잘 드러내는 이유는 몇 가지가 있다. 먼저 기존 테스트 케이스나 실제 사용 예시에서 좋은 seed input을 모을 수 있다. 그리고 버그를 드러내는 입력은 완전히 엉뚱한 입력이 아니라, 정상 입력과 아주 가까운 곳에 있는 경우가 많다. 예를 들어 숫자 하나가 너무 크거나, 구분자가 하나 더 있거나, 문자열 길이가 경계값을 넘는 정도의 차이로 버그가 발생할 수 있다.

또한 잘 작성된 프로그램은 보통 모듈화되어 있기 때문에, 입력의 특정 부분이 프로그램의 특정 컴포넌트와 연결된다. 예를 들어 URL에서 protocol 부분은 protocol parser와 관련되고, query string 부분은 parameter parser와 관련된다. 그래서 입력의 특정 짧은 부분만 바꿔도 특정 코드 영역의 동작을 집중적으로 흔들 수 있다. 이것을 locality가 존재한다고 볼 수 있다.

## Greybox Fuzzing

그다음 발전한 방식이 **greybox fuzzing**이다. 단순 mutation-based fuzzing은 입력을 변형하고 실행 결과를 보는 데 그치지만, greybox fuzzing은 프로그램의 내부 정보를 일부 활용한다. 특히 structural coverage, 즉 어떤 코드 경로가 실행되었는지를 보고 fuzzing 방향을 조정한다.

![](../images/Pasted%20image%2020260603212231.png)

흐름은 이렇다. 먼저 corpus, 즉 seed input 집합이 있다. 여기서 하나를 선택해서 mutation을 적용하고, 변형된 입력을 프로그램에 넣어 실행한다. 그 결과 crash가 나면 실패 입력으로 저장한다. crash가 나지 않더라도 새로운 코드 경로를 실행했다면 그 입력은 가치가 있으므로 다시 corpus에 추가한다. 반대로 기존과 같은 경로만 실행했다면 별로 새롭지 않기 때문에 버릴 수 있다.

즉, greybox fuzzing은 “아무 입력이나 많이 넣는 방식”이 아니라, **새로운 coverage를 만들어내는 입력을 살아남게 하는 방식**이다. 그래서 시간이 지날수록 corpus가 점점 더 다양한 실행 경로를 포함하게 되고, 프로그램의 깊은 부분까지 도달할 가능성이 커진다. AFL이나 libFuzzer가 이런 방식의 대표적인 도구다.

![](../images/Pasted%20image%2020260603212257.png)

마지막 알고리즘을 보면 전체 과정이 정리된다. 처음에는 seed 집합 `S`를 테스트 집합 `T`로 두고, 실패 입력 집합 `F`와 coverage 집합 `C`를 비워둔다. 먼저 기존 seed들을 실행해서 기본 coverage를 모은다. 이후 종료 조건이 만족될 때까지 `T`에서 입력 하나를 선택하고, mutation을 적용해서 새로운 입력 `t'`를 만든다. 이 입력으로 프로그램이 실패하면 `F`에 저장한다. 실패하지 않더라도 새로운 coverage가 있으면 `T`에 추가하고 coverage도 갱신한다.

여기서 seed selection, seed scheduling, strategic mutation, failure analysis, corpus management 같은 요소가 붙는 이유는 fuzzing이 단순 반복 작업처럼 보여도 실제 성능은 “어떤 seed를 고를지”, “어떤 mutation을 적용할지”, “어떤 입력을 계속 유지할지”에 크게 달려 있기 때문이다.

### Scalable automated test generation with greybox fuzze
앞에서 greybox fuzzing의 원리를 봤다면, 이제는 이 방식이 실제 산업 현장에서 얼마나 큰 규모로 사용되는지를 보는 흐름이다. 단순히 연구용 아이디어가 아니라, 실제 오픈소스 프로젝트나 대형 서비스에서 자동으로 버그를 찾는 핵심 기술로 쓰이고 있다는 점을 보여주는 부분이다.

Greybox fuzzer는 사람이 직접 테스트 케이스를 계속 만드는 방식보다 훨씬 확장성이 좋다. 프로그램에 seed input을 넣고, mutation을 만들고, 실행 결과와 coverage를 보고, 새로운 경로를 발견하면 다시 corpus에 추가하는 과정을 자동으로 반복할 수 있기 때문이다. 그래서 많은 프로젝트에 동시에 적용하기 좋고, 서버나 머신을 많이 붙이면 테스트 규모를 크게 늘릴 수 있다.

Google이 약 500개의 오픈소스 프로젝트에 greybox fuzzer를 돌리고, 25,000대 이상의 머신을 사용해서 41,360개 이상의 failure를 발견했다는 내용은 fuzzing이 실제로 대규모 자동 테스트 생성에 효과적이라는 근거로 볼 수 있다. 여기서 중요한 건 단순히 버그를 많이 찾았다는 것뿐만 아니라, release마다 fuzzing을 계속 돌린다는 점이다. 소프트웨어는 계속 수정되기 때문에, 이전에는 없던 버그가 새로운 코드 변경으로 생길 수 있다. 그래서 fuzzing은 한 번 하고 끝나는 테스트가 아니라, 지속적으로 수행해야 하는 자동화된 품질·보안 검증 과정이라고 볼 수 있다.

그래프에서 CVE ID 수가 시간이 지날수록 증가하는 것도 보안 취약점이 계속 발견되고 관리되고 있다는 흐름과 연결된다. 소프트웨어가 복잡해질수록 취약점도 계속 나오고, 이를 발견하기 위한 자동화 도구의 필요성이 커진다. 그래서 fuzzing은 단순한 crash 테스트를 넘어서 실제 보안 취약점 탐지와 연결된다.

그다음은 대표적인 greybox fuzzer 도구들이다.

### American Fuzzy Lop (AFL)
**AFL, American Fuzzy Lop**은 오픈소스 fuzzer이고, genetic algorithm을 이용해서 테스트 케이스의 code coverage를 효율적으로 늘린다. 여기서 genetic algorithm이라는 말은, 입력들을 계속 변형하고 그중 더 좋은 입력, 즉 새로운 코드 경로를 더 많이 실행하는 입력을 살아남게 하는 방식이라고 이해하면 된다. 앞에서 본 greybox fuzzing의 corpus 관리와 비슷하게, 더 유용한 입력을 선택하고 변형하면서 점점 테스트 범위를 넓혀가는 구조다.

AFL은 OpenSSL, Firefox, SQLite 같은 주요 오픈소스 프로젝트에서 중요한 버그를 찾는 데 사용되었다. 이런 프로젝트들은 실제로 많은 사람이 사용하는 소프트웨어이기 때문에, 여기서 발견되는 버그는 단순한 오류가 아니라 보안 취약점으로 이어질 가능성도 크다. AFL++는 AFL을 확장한 버전으로 보면 된다. 더 다양한 mutation, 더 나은 instrumentation, 성능 개선 등이 추가된 발전형 도구라고 이해하면 된다.

### LibFuzzer
**LibFuzzer**는 AFL에서 영감을 받은 greybox fuzzer이고, 주로 C/C++ 라이브러리를 테스트하는 데 사용된다. LLVM의 구성 요소로 개발되었기 때문에 LLVM 생태계와 잘 맞고, 특히 sanitizer들과 함께 쓰기 좋다. 예를 들어 AddressSanitizer를 같이 사용하면 단순히 프로그램이 crash되는지만 보는 것이 아니라, buffer overflow, use-after-free 같은 메모리 오류도 더 정확하게 잡을 수 있다.

# Malware
앞에서 fuzzing은 소프트웨어 안에 숨어 있는 버그나 취약점을 찾는 방법이었다. 이제는 그런 취약점이 실제 공격에서 어떻게 악용될 수 있는지를 보기 위해 **Malware**로 넘어간다. 즉, 버그와 취약점이 단순한 품질 문제가 아니라, 악성 소프트웨어가 시스템을 공격하는 통로가 될 수 있다는 흐름이다.

## Malicious Software
Malware는 **malicious software**, 즉 악의적인 목적을 가지고 만들어진 소프트웨어를 의미한다. 일반 프로그램은 사용자의 작업을 돕기 위해 만들어지지만, malware는 컴퓨터 시스템, 네트워크, 사용자에게 피해를 주거나 악용하기 위해 만들어진다.

주된 목적은 시스템 동작을 방해하거나, 민감한 정보를 빼내거나, 허가받지 않은 접근 권한을 얻는 것이다. 예를 들어 개인정보를 훔치거나, 계정 정보를 탈취하거나, 시스템 내부에 몰래 들어가 공격자가 다시 접속할 수 있는 통로를 만들 수 있다.

Malware가 퍼지는 방식도 다양하다. 감염된 이메일 첨부파일을 열게 만들거나, 악성 웹사이트에 접속하게 하거나, 정상 소프트웨어처럼 보이는 파일을 다운로드하게 만들 수 있다. 또는 이미 침해된 네트워크를 통해 내부 시스템으로 퍼질 수도 있다. 그래서 malware는 단순히 “이상한 파일을 실행해서 감염된다” 정도가 아니라, 여러 경로를 통해 유입될 수 있다고 봐야 한다.

Malware의 대표적인 종류로는 virus, worm, trojan horse가 있다.

---
### Virus
**Virus**는 정상 파일에 붙어서 퍼지는 악성 코드다. 사용자가 감염된 파일을 실행하면 virus도 같이 실행되고, 다른 파일에 붙으면서 확산될 수 있다. 핵심은 스스로 독립적으로 움직인다기보다, 정상 파일이나 프로그램에 붙어서 실행된다는 점이다.

### Worm
**Worm**은 자기 복제를 하면서 독립적으로 퍼지는 malware다. 특히 네트워크를 통해 다른 시스템으로 확산되는 경우가 많고, 운영체제나 서비스의 취약점을 이용해 전파될 수 있다. virus가 보통 감염된 파일 실행에 의존한다면, worm은 네트워크를 타고 스스로 퍼질 수 있다는 점이 차이다.

### Trojan Horse
**Trojan Horse**는 정상 소프트웨어처럼 위장한 malware다. 사용자가 보기에 유용한 프로그램이나 정상 파일처럼 보이기 때문에 속아서 설치하게 된다. 설치된 뒤에는 backdoor를 만들거나, 데이터를 훔치거나, 공격자가 원하는 악성 행위를 수행할 수 있다. 핵심은 기술적 취약점만 이용하는 것이 아니라, 사용자를 속이는 방식에 의존한다는 점이다.

### Ransomware
그다음은 **Ransomware**다. Ransomware는 사용자의 파일을 암호화해서 접근할 수 없게 만든 뒤, 복호화 키를 주는 대가로 돈을 요구하는 malware다. 보통 암호화폐로 돈을 요구하는 경우가 많다.

Ransomware가 위험한 이유는 단순히 파일 몇 개가 손상되는 수준이 아니라, 개인, 기업, 병원, 공공기관 같은 중요한 조직의 업무를 멈출 수 있기 때문이다. 특히 critical infrastructure에 영향을 주면 단순한 보안 사고가 아니라 사회적 피해로 이어질 수 있다.

---
# Deep Web

앞에서 malware를 봤다면, 이제는 그런 악성 행위가 어디에서 유통되거나 숨겨질 수 있는지로 넘어간다. 그래서 **Deep Web, Dark Web, Tor**가 나온다. 보안 관점에서는 단순히 “인터넷의 숨겨진 영역”을 설명하려는 게 아니라, 익명성과 비공개성이 공격자에게 어떻게 이용될 수 있는지를 이해하는 흐름이다.

## Deep Web
**Deep Web**은 일반 검색 엔진에 의해 색인되지 않는 인터넷 영역을 말한다. 우리가 구글이나 네이버에서 검색해서 바로 찾을 수 있는 웹페이지는 surface web이고, 로그인해야 볼 수 있는 페이지, 내부 DB에 저장된 정보, 개인 메일함, 학교 포털, 회사 내부 시스템처럼 검색 엔진이 접근하지 못하는 영역은 deep web에 포함된다.

중요한 건 deep web 자체가 불법적인 공간이라는 뜻은 아니라는 점이다. 오히려 대부분은 정상적인 이유로 검색되지 않는 정보다. 예를 들어 내 이메일, 은행 계좌 정보, 클라우드 저장소 파일은 검색 엔진에 노출되면 안 된다. 그래서 deep web은 “숨겨진 위험한 공간”이라기보다, **검색 엔진이 접근하거나 색인하지 않는 비공개 영역**으로 이해하면 된다.

---
## Dark Web
그다음 **Dark Web**은 deep web의 일부다. 다만 단순히 검색되지 않는 수준이 아니라, 의도적으로 숨겨져 있고 Tor 같은 특수한 소프트웨어를 통해서만 접근할 수 있는 영역이다. 그래서 deep web과 dark web은 같은 말이 아니다. deep web 안에 dark web이 포함되는 구조라고 보면 된다.

Dark web은 익명성을 제공하기 때문에 프라이버시 보호 목적으로 쓰일 수도 있지만, 동시에 불법 거래, 악성코드 유통, 탈취 정보 거래 같은 행위와 연결되는 경우가 많다. 그래서 보안 수업에서는 dark web을 공격 인프라나 사이버 범죄 생태계와 연결해서 다루는 것이다.

### Tor
여기서 Tor가 나온다. **Tor(The Onion Router)** 는 사용자의 익명성과 프라이버시를 강화하기 위한 네트워크다. 일반적으로 웹사이트에 접속하면 사용자의 IP 주소와 목적지가 비교적 직접적으로 연결된다. 하지만 Tor는 트래픽을 여러 relay node를 거쳐 전달해서, 누가 어디에 접속했는지 추적하기 어렵게 만든다.

![](../images/Pasted%20image%2020260603213032.png)

Tor의 핵심은 onion routing이다. 양파처럼 여러 겹으로 암호화된 데이터를 만들고, 각 노드는 자신이 알아야 하는 한 겹의 정보만 복호화한다. 예를 들어 Tor client가 entry node, middle relay, exit relay를 거쳐 목적지 서버로 간다고 하면, entry node는 사용자의 IP는 알 수 있지만 최종 목적지는 모른다. middle relay는 앞뒤 relay 정도만 알 수 있고, 사용자와 목적지를 직접 연결하지 못한다. exit relay는 최종 목적지로 데이터를 보내지만, 원래 사용자가 누구인지는 모른다.

즉, 각 노드가 전체 경로를 모두 알지 못하게 만드는 것이 핵심이다. 그래서 어느 한 노드만 관찰해서는 “이 사용자가 이 서버에 접속했다”를 알기 어렵다. 이 구조 때문에 Tor는 익명성을 제공할 수 있다.

다만 exit relay 이후 목적지 서버까지의 구간은 Tor 암호화가 끝나는 지점이기 때문에 주의가 필요하다. 목적지 서버가 HTTPS를 사용하지 않으면 exit relay가 내용을 볼 수 있을 가능성이 있다. 그래서 Tor를 사용한다고 해서 모든 통신 내용이 완전히 안전해지는 것은 아니고, HTTPS 같은 종단 간 암호화가 함께 필요하다.

# Zero-Day Attack
앞에서 dark web이나 malware처럼 공격이 유통되고 실행되는 환경을 봤다면, 이제는 공격자가 어떤 약점을 이용하는지로 넘어간다. 그중 가장 위험한 형태가 **zero-day attack**이다. 일반적인 취약점은 이미 알려져 있고 패치나 대응 방법이 존재할 수 있지만, zero-day는 아직 알려지지 않았거나 대응할 시간이 거의 없는 취약점을 이용한다는 점에서 훨씬 위험하다.

**Zero-day attack**은 소프트웨어 개발사나 일반 대중이 아직 모르는 취약점을 이용한 공격이다. 여기서 “zero-day”라는 말은 취약점이 발견된 날을 기준으로 방어자가 대응할 시간이 **0일**이라는 의미다. 즉, 취약점이 공개되거나 발견되자마자 공격이 이루어지거나, 심지어 개발사가 알기 전부터 공격자가 먼저 악용하는 상황을 말한다.

이게 위험한 이유는 방어가 제한적이기 때문이다. 이미 알려진 취약점이라면 패치를 적용하거나 탐지 규칙을 만들 수 있다. 그런데 zero-day는 아직 공식 패치가 없고, 보안 장비도 해당 공격 패턴을 모를 수 있다. 그래서 기존 방어 체계만으로는 탐지하거나 차단하기 어렵다.

또한 zero-day 공격은 빠른 대응이 필요하다. 취약점이 발견되면 개발사는 긴급 패치를 만들고, 사용자는 가능한 빨리 업데이트해야 한다. 시간이 지날수록 공격자가 해당 취약점을 더 널리 악용할 가능성이 커지기 때문이다. 그래서 zero-day는 단순한 버그라기보다, 발견 순간부터 공격과 방어가 동시에 시작되는 문제라고 볼 수 있다.

Zero-day는 APT와도 연결된다. APT는 특정 조직이나 국가, 기업을 장기간 은밀하게 공격하는 고도화된 공격을 의미하는데, 이런 공격에서는 알려지지 않은 취약점을 사용해 초기 침투를 시도하는 경우가 있다. 특히 중요한 기관이나 기업을 대상으로 할 때 zero-day는 매우 강력한 공격 수단이 될 수 있다.

## CVE (Common Vulnerabilities and Exposures)
그다음 나오는 **CVE**는 취약점을 식별하고 공유하기 위한 표준 이름 체계다. CVE는 Common Vulnerabilities and Exposures의 약자로, 보안 취약점에 고유한 번호를 붙여 관리하는 시스템이다. 예를 들어 특정 제품의 특정 취약점에 `CVE-연도-번호` 형태의 식별자가 붙으면, 보안 연구자, 개발사, 관리자들이 같은 취약점을 같은 이름으로 이야기할 수 있다.

CVE가 필요한 이유는 취약점 정보가 여러 곳에서 다르게 불리면 혼란이 생기기 때문이다. 어떤 사람은 “브라우저 원격 코드 실행 취약점”이라고 부르고, 다른 사람은 “특정 라이브러리 버그”라고 부르면 같은 문제인지 확인하기 어렵다. CVE ID가 있으면 “우리가 말하는 취약점이 정확히 이것이다”라고 공통 기준을 잡을 수 있다.

# APT Advanced Persistent Threat
앞에서 zero-day attack은 아직 알려지지 않았거나 대응이 어려운 취약점을 이용하는 공격이라고 했다. 이제는 그런 고급 공격이 실제로 어떤 방식으로 오래 지속되는지를 보기 위해 **APT**를 다룬다. 즉, APT는 단순히 한 번 침투하고 끝나는 공격이 아니라, 특정 대상을 정해서 오래 숨어 있으면서 정보를 빼내는 형태의 공격이라고 보면 된다.

**APT**는 Advanced Persistent Threat의 약자다. 이름을 나눠서 보면 이해하기 쉽다.  
Advanced는 고도화된 공격 기법을 사용한다는 뜻이고, Persistent는 공격이 장기간 지속된다는 뜻이다. Threat는 이런 공격 주체나 위협 자체를 의미한다.

APT 공격은 보통 불특정 다수를 대상으로 하는 일반적인 악성코드 공격과 다르다. 특정 기업, 정부기관, 연구소, 개인 등을 목표로 삼고, 그 조직 안에 몰래 들어간 뒤 오랫동안 들키지 않으면서 활동한다. 목적은 단순한 시스템 파괴보다는 기밀 정보 탈취, 내부 정찰, 장기적인 감시, 중요한 데이터 유출인 경우가 많다.

APT의 첫 번째 특징은 **advanced techniques**다. 공격자는 일반적인 malware만 사용하는 것이 아니라, zero-day 취약점, custom malware, 정교한 우회 기법 등을 사용할 수 있다. 특히 target에 맞춰 제작한 악성코드를 사용하면 일반 백신이나 탐지 시스템이 쉽게 알아차리지 못할 수 있다.

두 번째 특징은 **persistence**다. APT는 한 번 공격하고 빠지는 것이 아니라, 내부망에 오래 머무르려고 한다. 그래서 backdoor를 만들거나, 정상 계정처럼 보이는 접근 권한을 확보하거나, 탐지를 피하면서 지속적으로 접근할 방법을 유지한다. 이 때문에 공격이 몇 주, 몇 달, 심하면 몇 년 동안 발견되지 않을 수도 있다.

세 번째 특징은 **targeted**라는 점이다. 무작위로 아무나 공격하는 것이 아니라, 특정 조직이나 특정 사람을 노린다. 예를 들어 특정 회사의 기술 자료, 정부기관의 내부 문서, 연구소의 연구 데이터처럼 공격자가 원하는 명확한 목표가 있다. 그래서 공격 방식도 그 대상에 맞게 설계된다.

네 번째는 **custom malware**다. APT 공격자는 목표 조직의 환경에 맞춰 악성코드를 직접 제작하거나 수정할 수 있다. 일반적으로 널리 퍼진 malware보다 탐지하기 어렵고, 특정 시스템에서만 동작하도록 만들어질 수도 있다.

다음으로 **social engineering**도 중요한 특징이다. APT 공격이 꼭 기술적인 취약점만으로 시작되는 것은 아니다. 이메일, 첨부파일, 가짜 로그인 페이지, 내부 직원 사칭 등을 이용해서 사람을 속일 수 있다. 예를 들어 목표 조직 직원에게 업무 관련 문서처럼 보이는 악성 파일을 보내고, 사용자가 열면 내부 침투가 시작되는 방식이다.

마지막으로 **exfiltration**이 나온다. 공격자가 내부망에 들어간 뒤 최종적으로 원하는 것은 데이터를 밖으로 빼내는 것이다. 이때 한 번에 대량으로 빼내면 탐지될 수 있기 때문에, 조금씩 나누어 외부 서버로 전송하거나 정상 트래픽처럼 위장할 수 있다. 핵심은 내부에 오래 숨어 있으면서 중요한 정보를 조용히 빼내는 것이다.

# Steganography

앞에서 APT나 ransomware처럼 공격자가 시스템에 침투하고 악성 행위를 수행하는 방식을 봤다면, 이제는 악성 데이터나 명령을 **어떻게 숨겨서 전달할 수 있는지**를 보는 흐름이다. 여기서 나오는 개념이 **Steganography**다. 암호화가 “내용을 못 읽게 만드는 것”이라면, 스테가노그래피는 “메시지가 있다는 사실 자체를 숨기는 것”에 가깝다.

**Steganography**는 그리스어에서 온 말로, 대략 “감춰진 글쓰기”라는 의미를 가진다. 일반적인 cryptography는 메시지 내용을 암호화해서 제3자가 읽지 못하게 만든다. 예를 들어 암호문을 보면 내용은 모르더라도 “무언가 비밀 데이터가 있다”는 사실은 알 수 있다. 반면 steganography는 겉으로 보기에는 평범한 이미지나 파일처럼 보이게 만들고, 그 안에 데이터를 숨긴다.

![](../images/Pasted%20image%2020260603213842.png)

예를 들어 그림 파일 안에 어떤 데이터를 숨긴다고 해보면, 겉으로 보이는 이미지는 거의 변하지 않는다. 사람 눈으로 봤을 때는 원본 이미지와 숨겨진 데이터가 들어간 이미지가 같아 보일 수 있다. 하지만 실제 파일 내부의 일부 바이트나 픽셀 값에는 숨겨진 정보가 들어가 있을 수 있다.

![](../images/Pasted%20image%2020260603213904.png)

이 방식은 파일에서 잘 사용되지 않거나 분석 시 잘 보지 않는 영역을 이용할 수 있다. 예를 들어 파일 포맷에는 실제 화면 출력에 크게 영향을 주지 않는 메타데이터 영역이나, 무시되는 바이트 영역이 있을 수 있다. 공격자는 이런 부분에 데이터를 넣어서 일반적인 파일 검사나 사용 과정에서는 잘 드러나지 않게 만들 수 있다.

## Bit plane
이미지에서는 **bit plane** 개념이 자주 사용된다. 디지털 이미지는 픽셀로 구성되고, 각 픽셀은 색상 값을 가진다. 예를 들어 하나의 색상 값이 8비트라면, 가장 왼쪽 비트는 값에 큰 영향을 주는 MSB이고, 가장 오른쪽 비트는 값에 작은 영향을 주는 LSB다.

여기서 LSB, 즉 least significant bit를 조금 바꿔도 색상 변화는 거의 눈에 띄지 않는다. 예를 들어 픽셀 값이 100에서 101로 바뀌는 정도는 사람 눈으로 구분하기 어렵다. 그래서 이미지의 각 픽셀 LSB에 숨기고 싶은 데이터를 조금씩 넣으면, 겉보기에는 거의 같은 이미지인데 내부에는 메시지가 들어 있는 파일을 만들 수 있다. 이게 bit-plane steganography의 기본 아이디어다.

중요한 점은 steganography가 보안 방어뿐 아니라 공격에도 악용될 수 있다는 것이다. 예시에서는 ransomware와 연결된다. 공격자가 악성코드나 다운로드 주소, 실행에 필요한 데이터를 이미지 파일 내부에 숨겨두면, 겉으로는 단순한 이미지처럼 보일 수 있다. 사용자가 이미지 파일을 받았을 때 일반적인 시각적 확인만으로는 악성 데이터가 있는지 알기 어렵다.

![](../images/Pasted%20image%2020260603213949.png)

그림의 사례처럼 JPG 파일 안에 압축 파일이나 스크립트 관련 데이터가 숨어 있을 수 있고, 특정 악성코드가 실행되면서 그 숨겨진 데이터를 추출해 다음 단계 공격에 사용할 수 있다. 이후 ransomware가 실행되면 파일들이 암호화되고, 사용자는 복호화 키를 받기 위해 돈을 요구받게 된다.

즉, steganography는 “데이터를 암호화한다”보다 한 단계 더 은밀한 방식이다. 암호화된 데이터는 눈에 띄지만 내용을 알 수 없는 상태이고, steganography는 데이터가 숨어 있다는 사실 자체를 감추려는 방식이다. 그래서 악성코드 분석이나 보안 탐지에서는 파일 확장자나 겉보기 형태만 믿으면 안 되고, 파일 내부 구조나 비정상적인 바이트 패턴까지 확인할 필요가 있다.
