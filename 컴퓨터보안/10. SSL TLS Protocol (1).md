>“웹에서 클라이언트와 서버가 안전하게 통신하려면 어떤 구조가 필요한가?”

우리가 웹사이트에 접속할 때 보통 HTTP가 아니라 HTTPS를 사용한다. HTTPS는 HTTP 자체가 암호화된 것이 아니라, **HTTP 데이터를 TLS 위에 올려서 전송하는 구조**라고 보면 된다.

즉, TLS는 애플리케이션 계층의 데이터를 TCP 위에서 안전하게 전달할 수 있도록 해주는 보안 계층이다.

---
# Web Security Cosiderations

웹은 기본적으로 클라이언트 / 서버 구조이다. 사용자는 크롬 같은 브라우저 같은 클라이언트를 통해 서버에 요청을 보내고, 서버는 응답을 준다.

그런데 웹 사용자는 보안 전문가가 아닌 경우가 많다. 대부분의 사용자는 네트워크 중간에서 누가 데이터를 훔쳐볼 수 있는지, 서버가 진짜 서버인지, 데이터가 변조될 수 있는지 잘 모른다.

그래서 웹 보안에서는 사용자가 직접 보안을 챙기기보다는, 프로토콜 차원에서 자동으로 보안을 제공해야 한다.

여기서 TLS가 필요한 이유가 나온다. TLS는 사용자가 복잡한 보안 절차를 직접 알지 못해도, 브라우저와 서버 사이에서 자동으로 다음을 제공한다.

- 서버 인증
- 데이터 기밀성
- 데이터 무결성
- 세션 키 생성

즉, 웹 환경에서는 보안 지식이 없는 일반 사용자도 안전하게 서비스를 사용할 수 있어야 하므로 TLS 같은 표준 보안 프로토콜이 필요하다.

# Relative Location of Security Facilities in TCP/IP

보안 기능은 여러 계층에 넣을 수 있다.

![](../images/Pasted%20image%2020260519180124.png)

예를 들어 네트워크 계층에서는 IPsec 같은 방식으로 보안을 제공할 수 있고, 애플리케이션 계층에서는 애플리케이션 자체가 암호화를 직접 처리할 수도 있다.

TLS는 그중에서 **전송 계층 근처**, 정확히는 애플리케이션과 TCP 사이에 위치한다고 보면 된다.
그래서 HTTPS 는 HTTP + TLS 로 HTTP 메세지를 TLS가 감싸고, TLS가 암호화한 데이터를 TCP로 전송하는 구조라고 보면된다.

# SSL / TLS Protocol

SSL/TLS는 TCP 위에서 동작하는 보안 프로토콜이다. TCP는 신뢰성 있는 전송을 제공하지만, 보안은 제공하지 않는다.

TCP가 해주는 것은 다음과 같다.

```
데이터를 순서대로, 손실 없이 전달
```

하지만 TCP만으로는 다음 문제를 해결할 수 없다.

```
누가 훔쳐보는가?
중간에서 변조되지는 않았는가?
내가 접속한 서버가 진짜 서버인가?
```

TLS는 이 문제를 해결한다. TLS가 제공하는 핵심 기능은 세 가지이다.

##### **Authentication**  
클라이언트는 서버 인증서를 확인해서 이 서버가 진짜 서버인지 검증한다.
##### **Confidentiality**  
클라이언트와 서버가 공유한 대칭키로 데이터를 암호화한다.
##### **Integrity
전송 중 데이터가 변조되었는지 확인할 수 있다.

정리하면 TLS는 TCP 통신 위에 보안 기능을 얹어서, HTTP 같은 애플리케이션 데이터를 안전하게 전달하게 해준다.

---
TLS는 하나의 단순한 프로토콜이 아니라, 크게 두 계층으로 나뉜다.

![](../images/Pasted%20image%2020260519180509.png)

**TLS Handshake Protocol**은 통신을 시작하기 전에 보안 파라미터를 협상하는 단계이다. 즉, 어떤 TLS 버전을 쓸지, 어떤 암호 알고리즘을 쓸지, 서버 인증서는 유효한지, 세션 키는 어떻게 만들지 등을 정한다.

**TLS Record Protocol**은 실제 데이터를 안전하게 나누고, 암호화하고, 무결성을 붙여 전송하는 계층이다.

쉽게 말하면 다음과 같다.

- Handshake Protocol = 보안 통신을 시작하기 위한 준비 과정
- Record Protocol = 준비된 키로 실제 데이터를 안전하게 보내는 과정

즉, TLS는 처음부터 데이터를 바로 암호화해서 보내는 것이 아니라, 먼저 핸드셰이크를 통해 서로 사용할 보안 설정과 키를 정한 뒤, Record 계층에서 실제 데이터를 처리한다.

---
# Connection and Session

TLS에서는 **Connection**과 **Session**을 구분한다.

#### Connection
Connection은 실제 클라이언트와 서버 사이의 일시적인 통신 연결이다.  
즉, TCP 연결 하나와 비슷하게 생각하면 된다.

#### Session
Session은 클라이언트와 서버가 공유하는 보안 설정의 묶음이다. Handshake Protocol을 통해 만들어지며, 암호 알고리즘, master secret 같은 정보를 포함한다.
중요한 점은 하나의 Session이 여러 Connection에서 재사용될 수 있다는 것이다.

예를 들어 사용자가 같은 서버에 여러 번 접속할 때, 매번 처음부터 모든 핸드셰이크를 다시 수행하면 비용이 크다. 그래서 이전에 만든 Session을 재사용하면 더 빠르게 보안 연결을 만들 수 있다.

정리하면 다음과 같다.

- Session = 보안 설정의 묶음
- Connection = 실제 통신 링크

Session은 비교적 논리적인 개념이고, Connection은 실제 데이터가 오가는 연결이라고 보면 된다.

---
# Session State

Session State는 TLS 세션이 유지하기 위해 필요한 정보들이다.

- **Session Identifier**
	서버가 특정 세션을 식별하기 위해 선택한 바이트 문자열이다. 나중에 클라이언트가 같은 세션을 재사용하고 싶을 때 이 값을 사용할 수 있다.

- **Peer Certificate**
	상대방의 X.509 v3 인증서이다. 보통 웹에서는 서버 인증서가 여기에 해당한다.

- **Compression Method**
	TLS에서는 암호화하기 전에 데이터를 압축하는 방식이 정의되어 있었지만, 실제 보안 문제 때문에 현대 TLS에서는 압축을 거의 사용하지 않는다.

- **Cipher Spec**
	사용할 암호 알고리즘들의 집합이다. 예를 들어 키 교환 방식, 대칭키 암호 방식, MAC 또는 AEAD 방식 등을 포함한다.

즉, Session State는 “이 세션에서 어떤 보안 설정을 사용할 것인가?”에 대한 정보를 저장한다.

##### Master Secret
Session State에는 **Master Secret**도 포함된다. Master Secret은 클라이언트와 서버가 공유하는 48바이트 비밀값이다. 이 값은 직접 데이터를 암호화하는 키라기보다는, 이후 여러 실제 키를 만들어내는 핵심 재료라고 보면 된다.

TLS에서는 하나의 키만 사용하는 것이 아니라, 방향별로 여러 키를 만든다.

예를 들어 다음과 같은 키들이 필요하다.

- 클라이언트가 보낼 때 쓰는 MAC key
- 서버가 보낼 때 쓰는 MAC key
- 클라이언트가 보낼 때 쓰는 encryption key
- 서버가 보낼 때 쓰는 encryption key
- IV

이런 키들을 만들기 위한 중심 재료가 Master Secret이다.

##### Is Resumable
또한 **Is Resumable**이라는 값이 있다. 
이 세션을 나중에 다시 사용할 수 있는지 나타내는 플래그이다.

---
# Connection State

Connection State는 실제 연결 단위에서 필요한 정보이다. Session State가 비교적 장기적인 보안 설정이라면, Connection State는 현재 연결에서 실제로 데이터를 주고받을 때 필요한 상태값이다.

여기에는 **server random**과 **client random**이 있다. 
클라이언트와 서버가 각각 만든 랜덤 값이며, 키 생성 과정에서 사용된다.

또한 방향별 MAC key가 있다.

- Server write MAC key : 서버가 보내는 데이터의 MAC을 만들 때 사용
- Client write MAC key : 클라이언트가 보내는 데이터의 MAC을 만들 때 사용

그리고 방향별 암호화 키도 있다.

- Server write key : 서버가 데이터를 암호화할 때 쓰고, 클라이언트가 복호화할 때
- Client write key : 클라이언트가 데이터를 암호화할 때 쓰고, 서버가 복호화할 때

즉, TLS는 양방향 통신이기 때문에 클라이언트→서버, 서버→클라이언트 방향의 키를 따로 둔다.

---

Connection State에는 IV와 sequence number도 포함된다.

**IV**, 즉 Initialization Vector는 블록 암호 모드에서 초기 상태를 제공하는 값이다.  
CBC 같은 모드에서는 이전 암호문 블록이 다음 레코드의 IV처럼 사용되기도 한다.

**Sequence Number**는 각 방향별 메시지 번호이다.  
클라이언트가 보내는 메시지와 서버가 보내는 메시지에 각각 별도의 sequence number가 있다.이 sequence number는 무결성 검증에서 중요하다. 왜냐하면 공격자가 메시지를 재전송하거나 순서를 바꾸는 것을 막는 데 도움이 되기 때문이다.

예를 들어 중간 공격자가 예전 TLS 레코드를 다시 보내는 replay attack을 시도할 수 있다. 이때 sequence number가 MAC 계산에 포함되면, 같은 메시지를 단순히 다시 보내도 올바른 순서의 메시지로 인정되지 않는다.

---
# TLS Record Protocol

TLS Record Protocol은 실제 애플리케이션 데이터를 처리하는 계층이다.

핵심 기능은 두 가지이다.

- 첫 번째는 **Confidentiality**, 즉 기밀성이다.  
	Handshake Protocol에서 만들어진 공유 비밀키를 사용해서 데이터를 암호화한다.

- 두 번째는 **Message Integrity**, 즉 메시지 무결성이다.  
	역시 Handshake Protocol에서 만들어진 MAC key를 이용해서 메시지가 변조되지 않았는지 확인한다.

즉, Handshake Protocol이 “키를 만드는 과정”이라면, Record Protocol은 “그 키를 이용해서 실제 데이터를 보호하는 과정”이다.

---
# TLS Record Header

TLS Record에는 Header가 붙는다. 이 Header에는 이 레코드가 어떤 종류의 데이터인지, 어떤 버전의 TLS인지, 길이가 얼마인지 등이 들어간다.

![](../images/Pasted%20image%2020260530153938.png)

대표 필드는 다음과 같다.

**Content Type**은 이 레코드 안에 들어 있는 상위 프로토콜을 나타낸다.  
예를 들어 Handshake 메시지인지, Application Data인지, Alert인지 등을 구분한다.

**Major Version**과 **Minor Version**은 TLS 버전을 나타낸다.  
TLS 1.2의 경우 major version은 3, minor version은 3으로 표현된다.

**Compressed Length**는 레코드 payload의 길이를 나타낸다. 사실 이제는 압축을 하지 않아서 사용되지 않는 필드이다.

# Record Protocol 구조

RFC 5246, 즉 TLS 1.2 기준의 Record Protocol 구조를 보여준다.

![](../images/Pasted%20image%2020260530154144.png)

여기서는 앞에서 다룬 TLS Record Header와 마찬가지로 `type`, `version`, `length` 필드는 동일하게 존재한다. 다만 차이점은 그 뒤에 오는 `fragment`의 구조가 고정되어 있지 않고, `SecurityParameters.cipher_type`에 따라 달라진다는 점이다.

TLS에서 실제 데이터를 보호하는 방식은 선택된 cipher suite에 따라 달라진다. 따라서 TLS는 현재 설정된 `cipher_type`을 확인한 뒤, `fragment`를 다음 세 가지 구조 중 하나로 해석한다.

```text
case stream: GenericStreamCipher;
case block:  GenericBlockCipher;
case aead:   GenericAEADCipher;
```

즉, `type`, `version`, `length`는 모든 TLSCiphertext에서 공통으로 사용되는 헤더 정보이다. 반면 실제 암호화된 payload에 해당하는 `fragment`는 스트림 암호, 블록 암호, AEAD 암호 중 어떤 방식을 사용하는지에 따라 내부 구조가 달라진다.

정리하면, 이 부분은 TLS Record의 앞부분은 공통 형식으로 유지되지만, 실제 데이터 보호 방식은 cipher suite에 의해 결정된다는 것을 보여준다.

---
### 1. GenericBlockCipher

GenericBlockCipher는 TLS에서 **block cipher 방식으로 데이터를 보호할 때 사용하는 Record payload 구조**이다.

![](../images/Pasted%20image%2020260530162212.png)

먼저 애플리케이션 데이터는 한 번에 처리되지 않고, TLS record 단위로 나뉜다. 이 조각이 `content`가 된다. 이후 필요하면 압축을 수행(사실 수행하지 않음)하고, 데이터 변조 여부를 확인하기 위해 MAC을 붙인다.

block cipher는 고정된 블록 크기 단위로 암호화해야 하므로, `content`와 `MAC`만으로 길이가 맞지 않으면 `padding`을 추가한다. 그리고 padding이 얼마나 들어갔는지 알려주는 `padding_length`도 함께 포함한다.

그래서 실제로 암호화되는 부분은 다음과 같다.

```
content || MAC || padding || padding_length
```

그리고 CBC 같은 block cipher 모드에서는 암호화에 IV가 필요하기 때문에, Record 안에 IV도 함께 들어간다.

결과적으로 GenericBlockCipher는 다음 구조로 이해하면 된다.

![](../images/Pasted%20image%2020260530162453.png)

마지막으로 이 암호화된 fragment 앞에 TLS record header인 `type`, `version`, `length`가 붙으면서 최종 TLSCiphertext가 된다.

---
### 2. GenericAEADCipher

GenericAEADCipher는 TLS에서 **AEAD 방식으로 데이터를 보호할 때 사용하는 구조**이다. AEAD는 암호화와 무결성 검증을 따로 처리하지 않고, 하나의 방식 안에서 함께 처리한다. 대표적인 예가 `AES-GCM`이다.

구조는 다음처럼 이해하면 된다.

```
nonce_explicit || AEAD-Encrypt(content, additional_data)
```

여기서 `content`는 실제 보호할 데이터이고, TLS에서는 `TLSCompressed.fragment`가 plaintext로 들어간다.

```
plaintext = TLSCompressed.fragment
```

`nonce`는 암호화할 때 사용하는 값이다. 같은 키로 같은 nonce를 반복해서 사용하면 보안상 문제가 생기기 때문에, record마다 구분되는 nonce가 필요하다. 여기서 `nonce_explicit`은 record 안에 직접 포함되어 전달되는 nonce 부분이라고 보면 된다.

AEAD 방식에서 중요한 점은 `additional_data`이다.  
`additional_data`는 암호화되지는 않지만, 무결성 검증에는 포함되는 데이터이다.

여기서는 다음 값들이 additional data로 들어간다.

```
additional_data =seq_num || TLSCompressed.type || TLSCompressed.version || TLSCompressed.length
```

즉, 실제 content뿐만 아니라 record의 순서 번호, 타입, 버전, 길이 정보까지 함께 인증한다. 그래서 공격자가 데이터 내용뿐만 아니라 record의 메타데이터를 바꾸더라도 검증에 실패하게 된다.

정리하면 GenericAEADCipher는 다음 구조로 보면 된다.

![](../images/Pasted%20image%2020260530162959.png)

그리고 이 방식은 `GenericBlockCipher`처럼 MAC을 따로 붙이고 padding을 추가한 뒤 암호화하는 방식이 아니다. AEAD는 암호화와 인증 태그 생성을 한 번에 처리하기 때문에 구조가 더 단순하고, 현대 TLS에서 많이 사용된다.

# TLS Record Layer Payload

TLS Record Layer Payload는 TLS Record 안에 들어갈 수 있는 **상위 프로토콜 데이터의 형태**를 정리한 것이다.

TLS Record는 공통적으로 앞에 `type`, `version`, `length` 같은 record header를 가진다. 그런데 그 안에 들어가는 payload는 `ContentType`에 따라 달라진다.

![](../images/Pasted%20image%2020260530163225.png)

예를 들어 `Change Cipher Spec Protocol`은 매우 단순하다. payload가 1바이트이고, 값이 `1`이면 “이제부터 협상된 암호 설정을 적용하겠다”는 의미이다.

`Alert Protocol`은 2바이트로 구성된다.
`Level`은 경고의 심각도를 나타내고, `Alert`는 실제 오류나 알림의 종류를 나타낸다. 예를 들어 인증서 문제, 연결 종료, 복호화 실패 같은 상황을 표현할 수 있다.

`Handshake Protocol`은 조금 더 복잡하다.
`Type`은 ClientHello, ServerHello, Certificate 같은 handshake 메시지 종류를 나타낸다.  
`Length`는 뒤에 오는 handshake content의 길이를 나타내고, `Content`에는 실제 handshake 정보가 들어간다.

마지막으로 HTTP 같은 상위 계층 데이터는 `Opaque content` 형태로 들어간다.  
TLS 입장에서는 HTTP 데이터의 내부 구조를 해석하지 않고, 그냥 보호해야 할 바이트 데이터로 취급한다.

## client_hello
이 메시지를 통해 클라이언트는 “나는 이런 방식으로 TLS 통신을 할 수 있다”는 정보를 서버에게 전달한다.

구조를 보면 다음 정보들이 포함된다.

![](../images/Pasted%20image%2020260530163912.png)

#### client_version
`client_version`은 클라이언트가 사용하고 싶은 TLS 버전이다.  
예를 들어 TLS 1.2로 통신하고 싶다면 그 버전 정보를 여기에 담아 보낸다.
#### random
`random`은 클라이언트가 생성한 랜덤 값이다.  
이 값은 나중에 서버의 random 값과 함께 key 생성 과정에 사용된다. 즉, 매 연결마다 다른 키가 만들어지도록 도와주는 재료라고 보면 된다.
#### session_id
`session_id`는 기존에 만들어진 TLS 세션을 재사용하고 싶을 때 사용된다.  
만약 재사용할 세션이 없거나, 새 보안 파라미터를 만들고 싶다면 이 값은 비어 있을 수 있다.
#### cipher_suites
`cipher_suites`는 클라이언트가 지원하는 암호 알고리즘 조합 목록이다.  
예를 들어 어떤 키 교환 방식을 쓸 수 있는지, 어떤 대칭키 암호를 지원하는지, 어떤 해시/MAC 방식을 지원하는지를 목록으로 보낸다. 클라이언트가 선호하는 순서대로 보낸다는 점도 중요하다.

![](../images/Pasted%20image%2020260530164440.png)

이름이 길어 보이지만, 나누어서 보면 TLS에서 사용할 보안 알고리즘 조합을 의미한다.

```
TLS / ECDHE / ECDSA / AES_128_GCM / SHA256
```

`TLS`는 TLS 프로토콜에서 사용하는 cipher suite라는 뜻이다.

- `ECDHE`는 키 교환 방식이다. 클라이언트와 서버가 세션 키를 만들기 위해 사용하는 방식이고, 여기서는 임시 타원곡선 Diffie-Hellman을 사용한다. `E`가 붙은 이유는 ephemeral, 즉 매 연결마다 임시 키를 새로 만든다는 의미이다. 그래서 나중에 서버의 개인키가 유출되더라도 과거 통신 내용이 바로 복호화되지 않는 forward secrecy를 제공할 수 있다.

- `ECDSA`는 인증 방식이다. 서버가 자신의 인증서에 들어 있는 공개키와 대응되는 개인키를 가지고 있음을 증명할 때 사용된다. 쉽게 말하면, 클라이언트가 “이 서버가 진짜 인증서의 주인인가?”를 확인하는 데 쓰인다.

- `AES_128_GCM`은 실제 데이터를 암호화하는 방식이다. AES를 128비트 키로 사용하고, GCM 모드를 사용한다. GCM은 AEAD 방식이기 때문에 암호화와 무결성 검증을 함께 제공한다.

- `SHA256`은 해시 함수이다. TLS 내부에서 키 생성이나 handshake 검증 등에 사용된다.
#### compression_methods
`compression_methods`는 클라이언트가 지원하는 압축 방식 목록이다.  
다만 실제 현대 TLS에서는 보안 문제 때문에 압축을 거의 사용하지 않는다.
#### extensions
`extensions`는 추가 기능을 요청하기 위한 영역이다.  
예를 들어 서버 이름을 알려주는 SNI, HTTP/2 사용 여부를 협상하는 ALPN 같은 기능들이 extension으로 들어갈 수 있다.

## server_hello
`server_hello`는 클라이언트가 보낸 `client_hello`에 대해 서버가 응답하는 메시지이다. 클라이언트가 여러 선택지를 제안했다면, 서버는 그중에서 실제로 사용할 값을 하나씩 선택해서 알려준다.

![](../images/Pasted%20image%2020260530164647.png)

#### server_version
`server_version`은 실제로 사용할 TLS 버전이다. 클라이언트가 제안한 버전과 서버가 지원하는 버전을 비교해서, 둘 다 사용할 수 있는 버전이 선택된다.
#### random
`random`은 서버가 생성한 랜덤 값이다. 이 값은 `client_hello`의 random과 독립적으로 생성되어야 하며, 이후 master secret과 key material을 만드는 과정에 사용된다.
#### session_id
`session_id`는 이번 연결이 어떤 세션에 해당하는지를 나타낸다. 클라이언트가 `client_hello`에서 기존 `session_id`를 보냈다면, 서버는 자신의 session cache에서 해당 세션을 찾는다. 재사용 가능한 세션이면 그 세션을 사용하고, 아니면 새로운 세션을 만든다.
#### cipher_suite
`cipher_suite`는 서버가 최종적으로 선택한 하나의 암호 알고리즘 조합이다. 
클라이언트는 `cipher_suites`로 여러 후보를 보냈지만, 서버는 그중 하나만 선택한다. 예를 들어 `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256` 같은 값이 선택될 수 있다.
#### compression_method
`compression_method`도 마찬가지로 클라이언트가 제안한 목록 중 서버가 하나를 선택한 값이다. 다만 현대 TLS에서는 압축을 거의 사용하지 않기 때문에 보통 `null` 압축이 선택된다고 보면 된다.
#### extensions
`extensions`는 서버가 선택하거나 응답하는 추가 기능 목록이다.  
중요한 점은 서버가 아무 extension이나 마음대로 보내는 것이 아니라, 클라이언트가 `client_hello`에서 제안한 extension에 대해서만 응답할 수 있다는 것이다.

## certificate
`certificate` 메시지는 서버가 클라이언트에게 **자신의 인증서 체인**을 보내는 단계이다. 클라이언트는 이 인증서를 보고 “내가 접속한 서버가 진짜 맞는지”를 검증한다.

여기서 중요한 것은 `certificate_list`가 단일 인증서 하나가 아니라, **인증서들의 연속된 체인**이라는 점이다.

![](../images/Pasted%20image%2020260530164953.png)

가장 앞에는 반드시 **서버 자신의 인증서**가 온다. 그다음 인증서들은 바로 앞 인증서를 발급한 CA의 인증서이다. 즉, 뒤에 오는 인증서가 앞에 있는 인증서를 보증하는 구조다.

예를 들면 이런 식이다.

```
example.com 서버 인증서
→ Intermediate CA가 서명함

Intermediate CA 인증서
→ Root CA가 서명함

Root CA 인증서
→ 브라우저나 OS가 이미 신뢰하고 있음
```

클라이언트는 이 체인을 따라가면서 각 인증서의 서명이 올바른지 확인한다.  
최종적으로 신뢰할 수 있는 Root CA까지 연결되면, 서버 인증서를 신뢰할 수 있다고 판단한다.

다만 Root CA 인증서는 보통 서버가 보내지 않아도 된다. 왜냐하면 Root CA의 공개키는 브라우저나 운영체제의 신뢰 저장소에 이미 들어 있다고 가정하기 때문이다.

## server_key_exchange
`server_key_exchange`는 서버가 **키 교환에 필요한 추가 파라미터를 보내는 메시지**이다. 특히 Diffie-Hellman 계열처럼 키 교환을 위해 서버의 임시 공개값이 필요한 경우에 사용된다.

핵심은 선택된 `KeyExchangeAlgorithm`에 따라 이 메시지 안에 들어가는 내용이 달라진다는 점이다.

![](../images/Pasted%20image%2020260530165120.png)

`dh_anon`은 익명 Diffie-Hellman 방식이다. 서버가 DH 파라미터는 보내지만, 인증서 기반 서명이 없기 때문에 서버 인증이 되지 않는다. 그래서 중간자 공격에 취약하다.

`dhe_dss`와 `dhe_rsa`는 임시 Diffie-Hellman 값을 사용하는 방식이다.  
여기서 `DHE`의 `E`는 ephemeral, 즉 매 연결마다 임시 키를 새로 만든다는 뜻이다. 서버는 `ServerDHParams`를 보내고, 이 값이 진짜 서버가 보낸 것임을 증명하기 위해 서명도 함께 보낸다.

이때 서명 대상은 다음 값들이다.

```
client_random || server_random || ServerDHParams
```

`client_random`과 `server_random`까지 같이 서명하는 이유는, 이 키 교환 파라미터가 현재 핸드셰이크에 묶여 있다는 것을 보장하기 위해서이다. 공격자가 이전 세션의 값을 재사용하거나 중간에서 DH 파라미터를 바꿔치기하면 서명 검증에 실패한다.

`dhe_rsa`는 RSA 인증서의 개인키로 서명하는 방식이고, `dhe_dss`는 DSS/DSA 방식으로 서명하는 구조라고 보면 된다. 즉, DHE는 키 교환 방식이고, RSA/DSS는 그 키 교환 값을 인증하는 서명 방식이다.

반면 `rsa`, `dh_dss`, `dh_rsa`의 경우에는 `server_key_exchange`에 추가로 보낼 내용이 없다. 예를 들어 RSA key exchange에서는 서버의 RSA 공개키가 이미 certificate 메시지 안에 들어 있으므로, 별도의 ServerKeyExchange가 필요하지 않다.

## server_hello_done
`server_hello_done`은 서버가 `server_hello`와 관련된 메시지를 모두 보냈다는 것을 알리는 신호이다.

TLS Handshake에서 서버는 보통 다음과 같은 메시지들을 먼저 보낸다.

```
ServerHello
Certificate
ServerKeyExchange
ServerHelloDone
```

여기서 `server_hello_done`이 오면, 클라이언트는 “서버가 보낼 초기 핸드셰이크 정보는 끝났구나”라고 판단한다.

이후 클라이언트는 서버가 보낸 정보를 검증한다. 예를 들어 서버 인증서가 유효한지 확인하고, 서버가 선택한 TLS 버전이나 cipher suite, key exchange parameter가 사용할 수 있는 값인지 검사한다.

문제가 없다면 클라이언트는 자신의 키 교환 단계를 진행한다.  
즉, `client_key_exchange`를 보내면서 클라이언트 쪽 키 교환 정보를 서버에게 전달한다.

## client_key_exchange
`client_key_exchange`는 서버가 보낸 정보를 확인한 뒤, 클라이언트가 **키 교환에 필요한 자신의 값을 서버에게 보내는 단계**이다.

이 메시지의 내용은 선택된 `KeyExchangeAlgorithm`에 따라 달라진다.

![](../images/Pasted%20image%2020260530165948.png)

RSA key exchange를 사용하는 경우에는 클라이언트가 `pre-master secret`을 직접 생성한다. 그리고 서버 인증서에 들어 있던 RSA 공개키로 이 값을 암호화해서 서버에게 보낸다.

```
Client:
pre-master secret 생성
→ 서버 공개키로 암호화
→ EncryptedPreMasterSecret 전송
```

서버는 자신의 RSA 개인키로 이를 복호화해서 같은 `pre-master secret`을 얻는다. 이후 클라이언트와 서버는 이 값을 기반으로 `master secret`을 만들고, 실제 통신에 사용할 키들을 생성한다.

반대로 DHE나 DH 계열을 사용하는 경우에는 클라이언트가 자신의 Diffie-Hellman 공개값을 보낸다.

```
Client:
자신의 DH public value 전송
→ ClientDiffieHellmanPublic
```

이 경우 클라이언트와 서버는 서로의 DH 공개값과 자신의 개인값을 이용해서 같은 shared secret을 계산한다.

## key exchange
`server_key_exchange`와 `client_key_exchange`는 선택된 키 교환 방식에 따라 역할이 달라진다. 여기서는 대표적으로 **RSA key exchange**와 **Ephemeral DH key exchange**를 비교해서 보면 된다.

![](../images/Pasted%20image%2020260530170226.png)
### RSA key exchange
RSA 방식에서는 클라이언트가 `pre-master secret`을 직접 만든다. 그다음 서버 인증서에 들어 있던 **서버의 RSA 공개키**로 이 값을 암호화해서 서버에게 보낸다.

서버는 자신의 RSA 개인키로 복호화해서 같은 `pre-master secret`을 얻는다. 이후 클라이언트와 서버는 이 값을 기반으로 `master secret`을 만들고, 실제 데이터 암호화에 사용할 키들을 생성한다.

### Ephemeral DH key exchange
Ephemeral DH 방식에서는 클라이언트가 비밀값을 직접 만들어서 보내지 않는다. 
대신 클라이언트와 서버가 각각 자신의 DH 공개값을 교환하고, 각자 계산을 통해 같은 `pre-master secret`을 만든다.

1. 서버는 먼저 DH 파라미터와 자신의 임시 DH 공개값을 보낸다.  
	이때 이 값이 진짜 서버가 보낸 것임을 증명하기 위해 서버의 개인키로 서명한다.

2. 클라이언트도 자신의 DH 공개값을 서버에게 보낸다.

3. 양쪽은 서로의 공개값과 자신의 개인값을 이용해서 같은 공유 비밀값을 계산한다.

여기서 `Ephemeral`은 매 연결마다 임시 DH 키를 새로 만든다는 뜻이다.  
그래서 나중에 서버의 장기 개인키가 유출되더라도, 과거 세션의 `pre-master secret`을 복원하기 어렵다. 이 성질을 **Forward Secrecy**라고 한다.

# Cryptographic Computations
Cryptographic Computations는 TLS 핸드셰이크에서 **키 교환 결과를 실제 통신용 키들로 바꾸는 과정**이다.

키 교환이 끝나면 클라이언트와 서버는 같은 비밀값을 얻게 된다. 이 값을 바탕으로 **master secret**을 만든다. TLS 1.2에서 master secret은 한 세션에서 사용되는 48바이트 공유 비밀값이다.

하지만 master secret을 그대로 데이터 암호화에 사용하지는 않는다. master secret은 일종의 “키 생성 재료”이고, 여기서 실제 Record Protocol에서 사용할 여러 키를 만들어낸다.

![](../images/Pasted%20image%2020260530171002.png)

생성되는 값들은 다음 순서로 나뉜다.

- client_write_MAC_key
- server_write_MAC_key
- client_write_key
- server_write_key
- client_write_IV
- server_write_IV

`client_write_MAC_key`는 클라이언트가 보내는 데이터의 MAC을 만들 때 사용된다.  
`server_write_MAC_key`는 서버가 보내는 데이터의 MAC을 만들 때 사용된다.

`client_write_key`는 클라이언트가 보내는 데이터를 암호화할 때 사용하는 키이고, 서버는 같은 키로 복호화한다. 반대로 `server_write_key`는 서버가 보내는 데이터를 암호화할 때 사용하는 키이고, 클라이언트가 복호화할 때 사용한다.

즉, TLS는 양방향 통신이기 때문에 클라이언트 → 서버 방향과 서버 → 클라이언트 방향의 키를 따로 만든다. 키 재료는 PRF를 통해 생성된다.

여기서 `master_secret`은 키 교환으로부터 만들어진 중심 비밀값이고, `"key expansion"`은 이 PRF가 키 확장을 위한 것임을 구분하는 label이다.  
`server_random`과 `client_random`은 핸드셰이크 초반에 서로 주고받은 랜덤 값이다.

이렇게 만든 `key_block`을 필요한 길이만큼 앞에서부터 잘라서 MAC key, encryption key, IV로 사용하는 구조다.

PRF 내부에서는 `P_hash`가 사용된다.  

![](../images/Pasted%20image%2020260530171031.png)

`P_hash`는 HMAC을 반복해서 필요한 만큼 긴 출력을 만들어내는 함수이다.

```
PRF(secret, label, seed)= P_hash(secret, label || seed)
```

그리고 `P_hash`는 다음처럼 반복된다.

![](../images/Pasted%20image%2020260530171046.png)

즉, 한 번의 HMAC 출력만으로 키 재료가 부족할 수 있으니까, HMAC을 여러 번 반복해서 충분한 길이의 바이트열을 만든다고 보면 된다.

# PRF Function
PRF는 TLS에서 **하나의 비밀값으로부터 필요한 키 재료를 만들어내는 함수**이다.  
여기서 PRF는 `Pseudo-Random Function`이고, 입력으로 `secret`, `label`, `seed`를 받는다.

![](../images/Pasted%20image%2020260530171451.png)

`secret`은 키 생성의 중심이 되는 비밀값이다.  
예를 들어 master secret을 만들 때는 `pre-master secret`이 secret으로 들어가고, 실제 통신용 key material을 만들 때는 `master secret`이 secret으로 들어간다.

`label`은 이 PRF가 어떤 목적의 값을 만드는지 구분하기 위한 문자열이다.  
예를 들어 master secret을 만들 때는 `"master secret"`이라는 label을 사용하고, key material을 만들 때는 `"key expansion"`이라는 label을 사용한다.

`seed`는 랜덤성을 추가하기 위한 값이다.  
TLS에서는 클라이언트와 서버가 서로 보낸 random 값이 seed로 사용된다.

Master secret을 만들 때는 다음처럼 사용된다.

![](../images/Pasted%20image%2020260530171723.png)

즉, 키 교환으로 얻은 `pre-master secret`에 `"master secret"`이라는 label과 클라이언트/서버 random 값을 넣어서 48바이트의 master secret을 만든다.

그다음 실제 통신에 사용할 key material은 다음처럼 만든다.

![](../images/Pasted%20image%2020260530171733.png)

여기서는 master secret을 다시 PRF에 넣고, `"key expansion"`이라는 label을 사용해서 MAC key, encryption key, IV 등을 만들 수 있는 긴 key block을 생성한다.

중요한 점은 두 과정에서 random 값의 순서가 다르다는 것이다. 이렇게 label과 seed를 다르게 넣기 때문에, 같은 비밀값을 기반으로 하더라도 목적에 따라 서로 다른 결과가 나온다.

전체 구조는 다음처럼 이해하면 된다.

![](../images/Pasted%20image%2020260530172116.png)

```
PRF(Master secret, "key expansion", CR || SR)
→ P_hash 내부에서 HMAC 반복
→ 충분한 길이의 key material 생성
```

P_hash는 한 번의 hash 값만 만드는 것이 아니라, HMAC을 반복해서 필요한 만큼 긴 출력을 만든다. 

![](../images/Pasted%20image%2020260530172326.png)

그 결과로 나온 바이트열을 앞에서부터 잘라서 다음 키들로 사용한다.

```
client_write_MAC_key
server_write_MAC_key
client_write_key
server_write_key
client_write_IV
server_write_IV
```

# TLS Handshake Protocol

TLS Handshake는 크게 **서로 사용할 보안 조건을 정하는 단계**와 **서버가 인증서와 키 교환 정보를 보내는 단계**로 나눠서 볼 수 있다.

![](../images/Pasted%20image%2020260530172603.png)

### Phase 1
먼저 Phase 1에서는 클라이언트와 서버가 기본 보안 파라미터를 협상한다.

`client_hello`에서는 클라이언트가 자신이 지원하는 TLS 버전, cipher suite 목록, compression method, session ID, client random 등을 보낸다. 쉽게 말하면 “나는 이런 방식들을 지원한다”라고 서버에게 알려주는 단계이다.

서버는 `server_hello`로 응답하면서 그중 실제로 사용할 값을 선택한다. 즉, TLS 버전, cipher suite, compression method, session ID, server random 등이 여기서 확정된다.

### Phase 2
그다음 Phase 2에서는 서버가 인증과 키 교환에 필요한 정보를 보낸다.

`certificate`는 서버가 자신의 인증서 체인을 보내는 메시지이다. 클라이언트는 이를 통해 서버가 진짜 해당 도메인의 서버인지 검증한다.

`server_key_exchange`는 선택된 키 교환 방식에 따라 서버의 추가 키 교환 정보를 보내는 메시지이다. 특히 DHE/ECDHE처럼 임시 키를 사용하는 경우, 서버의 임시 공개값과 그에 대한 서명이 포함된다.

`certificate_request`는 서버가 클라이언트 인증서를 요구할 때 사용된다. 일반적인 웹 접속에서는 보통 서버 인증만 하기 때문에 생략되는 경우가 많다.

마지막으로 `server_hello_done`은 서버가 보낼 초기 핸드셰이크 메시지를 모두 보냈다는 의미이다. 이 메시지를 받은 클라이언트는 서버 인증서와 파라미터를 검증한 뒤, 자신의 키 교환 단계로 넘어간다.

---
![](../images/Pasted%20image%2020260530172738.png)

### Phase 3
Phase 3에서는 서버가 보낸 정보를 확인한 뒤, 클라이언트가 자신의 키 교환 정보를 서버에게 보낸다.

먼저 서버가 `certificate_request`를 보낸 경우에는 클라이언트도 자신의 인증서를 보낼 수 있다. 일반적인 HTTPS에서는 보통 서버만 인증하고 클라이언트 인증서는 요구하지 않기 때문에, 이 단계는 생략되는 경우가 많다.

그다음 핵심은 `client_key_exchange`이다.  
이 메시지를 통해 클라이언트는 키 교환에 필요한 값을 서버에게 보낸다.

- RSA 방식이면 클라이언트가 만든 `pre-master secret`을 서버 공개키로 암호화해서 보낸다.

- DHE/ECDHE 방식이면 클라이언트가 자신의 DH 공개값을 서버에게 보낸다.

이 과정이 끝나면 클라이언트와 서버는 같은 `pre-master secret` 또는 shared secret을 계산할 수 있다. 이후 이 값으로 `master secret`을 만들고, 다시 실제 통신용 키들을 생성한다.

`certificate_verify`는 클라이언트 인증서를 사용한 경우에 보내는 메시지이다.  
클라이언트가 “이 인증서의 개인키를 실제로 내가 가지고 있다”는 것을 증명하기 위해 서명값을 보낸다.

### Phase 4
Phase 4에서는 지금까지 협상한 암호 설정을 실제로 적용하고, 핸드셰이크를 마무리한다.

먼저 클라이언트가 `change_cipher_spec`을 보낸다.  
이 메시지는 “이제부터 내가 보내는 메시지는 협상된 키와 알고리즘으로 보호해서 보낼게”라는 의미이다.

그다음 클라이언트는 `finished` 메시지를 보낸다.  
`finished`는 새로 적용된 암호 설정으로 보호되는 첫 번째 메시지이며, 지금까지의 handshake 메시지들이 중간에서 변조되지 않았는지 검증하는 역할을 한다.

서버도 마찬가지로 `change_cipher_spec`을 보낸 뒤, `finished` 메시지를 보낸다.

양쪽의 `finished` 검증이 성공하면 TLS Handshake가 완료된다. 이후부터는 HTTP 같은 application data가 TLS Record Protocol을 통해 암호화되어 전송된다.
