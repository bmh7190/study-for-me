TLS 1.2에서는 오래된 암호 알고리즘이나 취약한 방식들이 여전히 선택지로 남아 있었다. 예를 들어 RC4, 3DES, MD5, SHA-1 같은 알고리즘은 시간이 지나면서 공격 가능성이 알려졌고, CBC-mode에서 MAC-then-encrypt 구조를 쓰는 방식도 여러 공격의 원인이 되었다. 또 static RSA처럼 서버의 개인키가 유출되면 과거 통신까지 복호화될 수 있는 방식도 문제가 있었다. 그래서 TLS 1.3에서는 이런 legacy 기능들을 과감하게 제거했다.

또 하나 중요한 이유는 **handshake 지연 시간 감소**다. TLS는 안전한 통신을 시작하기 전에 클라이언트와 서버가 버전, cipher suite, key exchange 방식, 인증서 등을 주고받아야 한다. TLS 1.2에서는 이 과정이 상대적으로 길었기 때문에, 실제 데이터를 보내기 전까지 시간이 더 걸렸다. TLS 1.3은 기본적으로 **1-RTT handshake**를 사용해서 연결 시작 시간을 줄였다. 쉽게 말하면, 왕복 통신 횟수를 줄여서 HTTPS 연결을 더 빠르게 만든 것이다.

그리고 TLS 1.3은 가능한 한 많은 handshake 내용을 암호화하려고 한다. TLS 1.2에서는 handshake 과정의 여러 정보가 평문으로 노출될 수 있었는데, TLS 1.3에서는 ServerHello 이후의 많은 메시지를 암호화한다. 그래서 중간 공격자가 통신 내용을 직접 보지는 못하더라도, 어떤 알고리즘을 협상하는지, 어떤 인증 정보가 오가는지 같은 메타데이터 노출도 줄이려는 방향으로 바뀐 것이다.

핵심 변화는 세 가지 정도로 정리할 수 있다.

첫째, **1-RTT handshake가 기본**이다. 기존보다 빠르게 안전한 연결을 만들 수 있고, 이전 세션을 재개할 때는 선택적으로 0-RTT도 사용할 수 있다. 다만 0-RTT는 replay attack 문제가 있을 수 있어서 항상 안전하게 쓸 수 있는 것은 아니다.

둘째, **AEAD-only cipher suite**만 사용한다. 즉, 암호화와 무결성 검증을 따로 어설프게 조합하는 방식이 아니라, AES-GCM이나 ChaCha20-Poly1305처럼 기밀성과 무결성을 함께 제공하는 방식만 허용한다. 그래서 CBC-mode MAC-then-encrypt 같은 오래된 구조가 제거된다.

셋째, **ECDHE-only key exchange**를 사용한다. 이는 forward secrecy를 보장하기 위한 선택이다. 즉, 나중에 서버의 장기 개인키가 유출되더라도 과거 통신 세션 키까지 바로 복구되지는 않도록 만든다. TLS 1.2의 static RSA 방식보다 훨씬 안전한 구조다.

# Handshake

handshake가 TLS 1.3에서 달라지는지 비교해서 한번 확인해보자.
**TLS 1.3은 더 빠르고, 더 많이 암호화된 상태로 handshake를 진행한다.**

![](../images/Pasted%20image%2020260603192238.png)

### TLS 1.2
먼저 TLS 1.2를 보면, full handshake에 기본적으로 **2-RTT**가 필요하다. RTT는 client와 server 사이에서 요청이 갔다가 응답이 돌아오는 한 번의 왕복 시간이다. TLS 1.2에서는 client가 `ClientHello`를 보내면, server가 `ServerHello`, `Certificate`, `ServerKeyExchange`, `ServerHelloDone`을 보낸다. 그다음 client가 `ClientKeyExchange`, `ChangeCipherSpec`, `Finished`를 보내고, server도 다시 `ChangeCipherSpec`, `Finished`를 보내야 한다. 이 과정을 다 끝낸 뒤에야 Application Data를 보낼 수 있다.

즉, TLS 1.2에서는 실제 데이터를 보내기 전에 주고받아야 할 메시지가 많고, 연결을 안전하게 만들기까지 시간이 더 걸린다. 또한 그림에서 회색 화살표로 표시된 것처럼 handshake의 많은 부분이 평문으로 오간다. 그래서 통신 내용 자체는 나중에 암호화되더라도, handshake 중에 어떤 인증서가 오가는지, 어떤 방식으로 협상되는지 같은 정보가 더 많이 노출될 수 있다.

### TLS 1.3
반면 TLS 1.3은 기본적으로 **1-RTT full handshake**를 사용한다. client가 처음 `ClientHello`를 보낼 때 단순히 “나 접속할게”만 보내는 것이 아니라, 지원하는 버전, signature algorithm, key share 같은 정보를 같이 보낸다. 여기서 중요한 점은 **key share를 처음부터 보낸다**는 것이다. TLS 1.2에서는 key exchange에 필요한 정보가 여러 단계에 걸쳐 오갔다면, TLS 1.3은 처음부터 키 교환에 필요한 재료를 함께 보내서 왕복 횟수를 줄인다.

server는 그에 대한 응답으로 `ServerHello`와 자신의 key share를 보내고, 이 시점 이후부터는 handshake key를 만들 수 있다. 그래서 `EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished` 같은 메시지는 암호화된 상태로 전달된다. 그림에서 초록색으로 표시된 부분이 바로 이 암호화된 구간이다.

> `CertificateVerify`는 서버가 보낸 인증서 안의 공개키가 실제로 서버가 가진 개인키와 대응되는지 확인하기 위해 사용된다. 서버는 지금까지의 handshake 메시지들을 모아 해시한 뒤, 그 해시값에 자신의 개인키로 서명해서 `CertificateVerify` 메시지로 보낸다. 클라이언트는 인증서에 들어 있는 서버의 공개키로 이 서명을 검증한다. 검증에 성공하면, 해당 인증서의 공개키가 실제 서버가 가진 개인키와 연결되어 있다는 것을 확인할 수 있다.

TLS 1.3에서 특히 중요한 변화는 server 쪽 인증서도 대부분 암호화되어 전달된다는 점이다. TLS 1.2에서는 server 인증서가 평문으로 전달되었지만, TLS 1.3에서는 `ServerHello` 이후에 키가 만들어지기 때문에 인증서 관련 메시지도 보호할 수 있다. 그래서 단순히 데이터 암호화만 강화한 것이 아니라, handshake 과정에서 노출되는 정보까지 줄인 구조라고 볼 수 있다.

또한 TLS 1.3에서는 server가 `Finished`를 보낸 뒤, client도 `Finished`를 보내면서 바로 Application Data를 이어서 보낼 수 있다. 그래서 TLS 1.2보다 실제 데이터 전송이 더 빨리 시작된다. 이게 TLS 1.3이 지연 시간을 줄였다고 하는 이유다.

> TLS 1.2에서는 `Finished` 메시지를 보호할 때 사용하는 키와 이후 Application Data를 암호화할 때 사용하는 키가 명확하게 분리되지 않은 구조였다. 반면 TLS 1.3에서는 `Finished`와 Application Data가 거의 이어서 전송될 수 있지만, 두 단계에서 사용하는 키를 분리한다. 이는 handshake를 마무리하는 과정과 실제 데이터를 보호하는 과정을 구분하기 위한 것이다. 이렇게 키를 분리하면 한쪽에서 문제가 생기더라도 다른 단계에 미치는 영향을 줄일 수 있고, 전체 보안성이 더 좋아진다.

# Version Negotiation on the Wire
TLS 1.3 handshake에서도 `ClientHello`와 `ServerHello` 안에 `legacy_version`이라는 필드가 있다. 그런데 이 값은 실제 TLS 1.3을 의미하는 `0x0304`가 아니라, 계속 `0x0303`으로 들어간다. `0x0303`은 TLS 1.2를 의미한다. 그래서 패킷을 겉으로만 보면 “이거 TLS 1.2 아닌가?”처럼 보일 수 있다.

![](../images/Pasted%20image%2020260603192906.png)

그런데 실제로 TLS 1.3을 사용하는지는 `legacy_version`이 아니라 `supported_versions` extension을 봐야 한다. 

왼쪽의 `ClientHello`를 보면 `legacy_version = 0x0303`으로 되어 있지만, 아래쪽 extension에 `supported_versions = [0x0304]`가 들어 있다. 이게 실제로는 TLS 1.3을 쓰고 싶다는 의미다. 여기에 `key_share`, `psk_key_exchange_modes`, `signature_algorithms` 같은 정보도 같이 들어가는데, 이는 TLS 1.3에서 handshake를 빠르게 하기 위해 처음부터 필요한 협상 정보를 많이 보내기 때문이다.

오른쪽의 `ServerHello`도 마찬가지다. `legacy_version`은 여전히 `0x0303`으로 남아 있지만, extension의 `supported_versions = 0x0304`를 통해 서버가 TLS 1.3을 선택했다는 것을 알려준다. 그리고 `key_share`에 서버의 ephemeral public key가 들어가면서 이후 handshake traffic key를 만들 수 있게 된다.

이렇게 한 이유는 **호환성 문제** 때문이다. 인터넷 중간에는 방화벽, 프록시, 로드밸런서 같은 장비들이 많이 있다. 이런 장비들 중 일부는 기존 TLS 구조만 예상하고 동작하기 때문에, 갑자기 `legacy_version = 0x0304` 같은 새로운 값을 보면 비정상 패킷으로 판단하거나 연결을 끊을 수 있다. 그래서 TLS 1.3은 겉모양은 TLS 1.2처럼 유지하고, 실제 TLS 1.3 사용 여부는 extension 안에서 협상하는 방식을 택했다.

# Middlebox Compatibility Mode

TLS 1.3은 실제로는 TLS 1.3 방식으로 동작하지만, 네트워크 상에서 보이는 형식은 일부러 TLS 1.2처럼 보이게 만든다. 이유는 중간 장비들 때문이다. 

기존 middlebox들은 TLS 1.2 형식을 기준으로 동작하도록 만들어진 경우가 많다. 예를 들어 이 장비들은 대략적으로 `ClientHello → ServerHello → ChangeCipherSpec → encrypted data` 같은 흐름을 기대한다. 그런데 TLS 1.3이 갑자기 새로운 형식으로만 동작하면, 일부 middlebox가 “이상한 TLS 패킷이다”라고 판단해서 TCP RST를 보내거나 조용히 패킷을 버릴 수 있다. 그래서 TLS 1.3은 실제 보안 구조와 별개로, wire format은 TLS 1.2처럼 보이도록 유지한다.

#### Legacy_version
첫 번째로 `legacy_version = 0x0303`이 유지된다. `0x0303`은 TLS 1.2를 의미하는 값이다. 하지만 실제 TLS 1.3 여부는 이 필드가 아니라 `supported_versions` extension 안의 `0x0304`를 보고 판단한다. 즉, 겉에 보이는 record header는 TLS 1.2처럼 두고, 진짜 버전 정보는 확장 필드 안에 넣은 것이다.

#### Dummy ChnageCipherSpec record
두 번째로 **dummy ChangeCipherSpec record**가 들어간다. TLS 1.2에서는 평문 handshake를 하다가 `ChangeCipherSpec` 이후부터 암호화된 데이터로 넘어가는 흐름이 있었다. TLS 1.3에서는 원래 이 메시지가 본질적으로 필요하지 않지만, middlebox가 기존 TLS 1.2 흐름을 기대하기 때문에 의미 없는 `ChangeCipherSpec`을 특정 시점에 보내준다. 쉽게 말하면 “나 TLS 1.2처럼 정상적으로 암호화 단계로 넘어가고 있어”라고 중간 장비를 안심시키기 위한 더미 메시지다.

#### Legacy_session_id
세 번째로 `legacy_session_id`를 비워두지 않고 사용한다. TLS 1.2에서는 session resumption을 위해 session id가 사용될 수 있었는데, TLS 1.3에서는 구조가 달라졌다. 그런데도 client는 32-byte random session id를 보내고, server도 이를 echo한다. 이렇게 하면 흐름이 TLS 1.2의 session resumption 시도처럼 보이기 때문에 기존 middlebox와의 호환성이 좋아진다.

#### Legacy_compression_methods
네 번째로 `legacy_compression_methods = [0x00]`도 남아 있다. TLS 1.3에서는 압축 기능이 제거되었다. 압축은 CRIME 같은 공격과 관련이 있었기 때문에 보안상 제거하는 것이 맞다. 하지만 필드 자체를 없애버리면 기존 형식을 기대하는 장비들이 문제를 일으킬 수 있으므로, 필드는 남겨두고 값은 `null`을 의미하는 `0x00`으로 고정한다.

# RFC 8446 Appendix D.4 : Dummy CCS Timing
TLS 1.3에서는 원래 TLS 1.2처럼 `ChangeCipherSpec`이 꼭 필요하지 않다. TLS 1.2에서는 “이제부터 암호화된 메시지로 전환한다”는 의미로 `ChangeCipherSpec`을 사용했지만, TLS 1.3에서는 키 스케줄이 달라져서 handshake traffic key, application traffic key가 단계별로 따로 만들어진다. TLS 자료에서도 TLS는 handshake를 통해 암호학적 파라미터와 키 재료를 만들고, 이후 record protocol에서 기밀성과 무결성을 제공하는 구조로 설명된다.

그런데 문제는 중간 장비들이 TLS 1.2의 흐름을 기대한다는 점이다. TLS 1.2에서는 보통 평문 handshake가 오가다가 `ChangeCipherSpec` 이후 암호화된 데이터가 나오는 패턴이었다. 그래서 TLS 1.3에서도 실제로는 필요 없지만, 중간 장비가 보기에는 “아, 이제 암호화 구간으로 넘어가는구나”라고 인식하도록 가짜 CCS를 보내는 것이다.

여기서 중요한 문장은 이것이다.

> **각 측은 다음 패킷이 middlebox 관점에서 암호화된 메시지로 바뀌는 순간에 fake ChangeCipherSpec을 보낸다.**

즉, dummy CCS는 아무 때나 넣는 것이 아니라, **바로 다음에 오는 메시지가 암호화된 것처럼 보이는 시점 직전에 넣는다.**

![](../images/Pasted%20image%2020260603193759.png)

먼저 server 쪽을 보면, server는 `ServerHello`를 보낸 직후 dummy CCS를 보낸다. 이유는 그다음에 오는 `EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished`가 암호화된 handshake 메시지이기 때문이다. middlebox 입장에서는 `ServerHello` 다음에 갑자기 암호화된 데이터가 나오면 이상하게 볼 수 있다. 그래서 server는 `ServerHello` 직후에 dummy CCS를 보내서 TLS 1.2처럼 “이제부터 암호화로 전환됨”이라는 모양을 만들어준다.

client 쪽도 비슷하다. 1-RTT handshake에서는 client가 `ServerHello`를 받은 뒤, 자신의 두 번째 flight를 보낸다. 여기에는 보통 `Finished`가 들어가고, 경우에 따라 바로 Application Data도 이어질 수 있다. 이 메시지들도 암호화된 상태로 나가기 때문에, client는 그 전에 dummy CCS를 보낸다. 즉, client 입장에서도 “이제부터 암호화된 메시지를 보낸다”는 TLS 1.2식 모양을 흉내 내는 것이다.

0-RTT의 경우에는 타이밍이 조금 다르다. client가 이전 세션 정보를 이용해 Early Data를 바로 보낼 수 있기 때문에, 첫 `ClientHello` 직후에 Early Data가 나갈 수 있다. 이때도 middlebox 입장에서는 갑자기 암호화된 데이터가 나오는 것처럼 보일 수 있으므로, client는 Early Data를 보내기 전에 dummy CCS를 넣는다.

![](../images/Pasted%20image%2020260603194027.png)

```text

9644  Application Data
9645  Change Cipher Spec, Application Data
```

겉으로 보면 조금 이상해 보일 수 있다. TLS 1.3인데 `Change Cipher Spec`이 보이고, 아직 실제 웹 데이터가 오가기 전인데 `Application Data`라고 표시되는 부분도 있다. 그런데 이건 TLS 1.3의 구조를 Wireshark가 record 단위로 표시하기 때문에 그렇게 보이는 것이다.

먼저 `9639 Client Hello`는 클라이언트가 서버에게 TLS 연결을 시작하자고 보내는 메시지다. 이때 겉으로는 TLS 1.2 형식처럼 보이지만, 내부 extension에는 `supported_versions = 0x0304`가 들어 있다. 이 값이 실제 TLS 1.3을 의미한다. 또한 `key_share`도 같이 들어 있어서, 클라이언트가 처음부터 키 교환에 필요한 공개값을 보낸다.

다음 `9641 Server Hello, Change Cipher Spec`은 서버가 응답하는 부분이다. 여기서 서버는 `ServerHello`를 보내고, 바로 이어서 dummy CCS를 보낸다. 이게 앞에서 말한 **D.4 Rule 1**이다. 서버 입장에서는 `ServerHello` 다음에 `EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished` 같은 암호화된 handshake 메시지를 보내야 한다. 그래서 그 직전에 middlebox가 TLS 1.2 흐름처럼 인식하도록 dummy CCS를 끼워 넣는다.

그다음 `9644 Application Data`가 중요하다. 이름만 보면 진짜 웹 데이터처럼 보이지만, 실제로는 아직 일반적인 HTTP 응답 데이터라기보다는 암호화된 handshake 메시지다. TLS 1.3에서는 `EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished`가 암호화되어 전달되기 때문에, Wireshark가 복호화하지 못하면 그냥 `Application Data`처럼 보일 수 있다. 표에서도 이 부분을 `Encrypted(Extensions + Certificate + CertificateVerify + Finished)`라고 설명하고 있다.

즉, `9644 Application Data`는 “진짜 서비스 데이터가 왔다”는 의미로만 보면 안 된다. 이 시점에서는 서버가 자신의 인증서와 서명 검증 정보, handshake 마무리 메시지를 암호화해서 보내는 구간이라고 보는 게 맞다.

마지막 `9645 Change Cipher Spec, Application Data`는 클라이언트 쪽에서 보내는 부분이다. 클라이언트도 서버의 `ServerHello`를 받은 뒤 자신의 암호화된 메시지를 보내기 전에 dummy CCS를 보낸다. 이게 **D.4 Rule 2**이다. 그리고 바로 이어서 암호화된 `Finished`를 보내고, 경우에 따라 실제 Application Data도 함께 보낼 수 있다.

여기서 중요한 점은 dummy CCS가 보이더라도 TLS 1.3의 1-RTT 구조가 깨지는 것은 아니라는 점이다. `Change Cipher Spec`은 추가로 응답을 기다리는 메시지가 아니라, 기존 흐름 안에 끼워 넣는 호환성용 record다. 그래서 패킷 목록에는 보이지만, `새로운 왕복 지연을 만들지는 않는다`.

# Cipher Suites & Key Exchange

![](../images/Pasted%20image%2020260603194248.png)

### TLS 1.2
TLS 1.2에서는 cipher suite 이름 안에 여러 정보가 한꺼번에 들어 있었다. 예를 들어 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`이라는 이름을 보면 다음 정보를 모두 알 수 있다.

- ECDHE      → key exchange 방식
- RSA        → authentication/signature 방식
- AES_128_GCM → 대칭키 암호화 방식
- SHA256     → MAC 또는 PRF hash

즉, TLS 1.2의 cipher suite는 “키 교환은 뭘 쓰고, 서버 인증은 뭘 쓰고, 데이터 암호화는 뭘 쓰고, 해시는 뭘 쓰는지”를 한 번에 묶어서 표현했다.

### TLS 1.3
그런데 TLS 1.3에서는 이 구조가 바뀐다. TLS 1.3의 cipher suite 이름은 예를 들어 `TLS_AES_128_GCM_SHA256`처럼 훨씬 짧다. 여기에는 주로 두 가지 정보만 남는다.

- AES_128_GCM → AEAD cipher
- SHA256      → HKDF / Finished에 사용할 hash

즉, TLS 1.3의 cipher suite에는 더 이상 `ECDHE`나 `RSA` 같은 key exchange, authentication 정보가 들어가지 않는다. 이 부분들이 사라진 것이 아니라, **별도의 extension을 통해 따로 협상**된다.

여기서 TLS 1.3이 **AEAD-only cipher suite**를 사용한다는 점도 중요하다. AEAD는 encryption과 authentication을 같이 제공하는 방식이다. 예를 들어 AES-GCM은 데이터를 암호화하면서 동시에 무결성 검증용 tag도 만든다. 그래서 TLS 1.2에서 문제가 되었던 “암호화 따로, MAC 따로” 같은 복잡한 조합을 줄일 수 있다.

또한 TLS 1.3은 key exchange로 반드시 `(EC)DHE` 계열을 사용한다. 즉, RSA로 premaster secret을 직접 암호화해서 보내는 static RSA 방식은 제거되었다. 이유는 **forward secrecy** 때문이다. ECDHE나 DHE는 매 세션마다 임시 key share를 사용해서 세션 키를 만든다. 그래서 나중에 서버의 장기 개인키가 유출되더라도, 과거 세션의 트래픽을 바로 복호화하기 어렵다.

TLS 1.3에서는 key exchange group과 signature algorithm을 따로 협상한다. 예를 들어 `supported_groups` extension에서는 `x25519`, `secp256r1` 같은 ECDHE 그룹을 협상하고, `signature_algorithms` extension에서는 `rsa_pss_rsae_sha256`, `ecdsa_secp256r1_sha256` 같은 서명 알고리즘을 협상한다.

이렇게 분리한 이유는 구조를 더 명확하게 만들기 위해서다. TLS 1.2처럼 모든 조합을 cipher suite 이름에 넣으면 가능한 조합이 너무 많아지고, 오래된 알고리즘도 계속 남아 있게 된다. 반면 TLS 1.3은 cipher suite에는 데이터 보호에 필요한 AEAD와 hash만 남기고, 키 교환과 인증 방식은 extension으로 따로 협상한다.

# AEAD Record Layer

먼저 AEAD에서 AAD는 **Additional Authenticated Data**이다. 이 값은 암호화되지는 않지만, 무결성 검증에는 포함된다. 즉, 공격자가 AAD에 해당하는 값을 바꾸면 복호화 과정에서 tag 검증이 실패한다. TLS 자료에서도 TLS Record Protocol은 기밀성과 무결성을 제공하는 계층으로 설명된다.

![](../images/Pasted%20image%2020260603194618.png)

TLS 1.2 AEAD에서는 AAD가 총 **13 bytes**였다.

```text
seq_num  8B
type     1B
version  2B
length   2B
```

여기서 `seq_num`은 record 순서를 나타내는 번호다. TLS record는 여러 개가 연속해서 오기 때문에, 중간에 record가 삭제되거나 순서가 바뀌면 탐지할 수 있어야 한다. 그래서 TLS 1.2에서는 sequence number를 AAD에 직접 포함해서 인증했다.

반면 TLS 1.3에서는 AAD가 **5 bytes**로 줄어든다.

```text
opaque_type     1B
legacy_version 2B
length         2B
```

여기서 `opaque_type`은 겉으로 보이는 record type이다. TLS 1.3에서는 암호화된 record가 바깥에서는 보통 application_data처럼 보이도록 처리된다. `legacy_version`은 호환성을 위해 남아 있는 버전 필드이고, `length`는 record 길이다.

중요한 차이는 TLS 1.3 AAD에는 `seq_num`이 직접 들어가지 않는다는 점이다. 대신 sequence number는 오른쪽에 나온 것처럼 **nonce 계산에 사용**된다.

```text
nonce = static_iv XOR padded(seq_num)
```

TLS 1.3에서 nonce는 패킷에 직접 실어서 보내는 값이 아니라, 양쪽이 이미 알고 있는 값으로 **각자 계산해서 만든다**. 여기서 `static_iv`는 handshake 과정에서 traffic secret으로부터 파생된 값이고, `seq_num`은 client와 server가 각자 record를 보낼 때마다 0, 1, 2, 3…처럼 증가시키는 sequence number다.

즉, TLS 1.3에서는 각 record마다 고유한 nonce를 만들기 위해 sequence number를 사용한다. AEAD 암호에서는 같은 key와 같은 nonce를 재사용하면 치명적인 문제가 생길 수 있다. 그래서 record마다 증가하는 `seq_num`을 `static_iv`와 XOR해서 매번 다른 nonce를 만든다.

# Downgrade Protection the DOWNGRD Canary

앞에서 봤듯이 TLS 1.3은 middlebox 호환성을 위해 record header의 version을 `0x0303`, 즉 TLS 1.2처럼 보이게 유지한다. 실제 TLS 1.3 여부는 `supported_versions` extension 안에서 확인한다. 그런데 이렇게 하면 공격자가 중간에서 개입해서 “둘 다 TLS 1.3을 지원하지만, TLS 1.2로 연결하게 만들자”는 식의 공격을 시도할 수 있다.

이게 **downgrade attack**이다.

![](../images/Pasted%20image%2020260603195234.png)

예를 들어 client와 server가 둘 다 TLS 1.3을 지원한다고 하자. 그런데 MITM 공격자가 중간에서 메시지를 조작해서 client가 TLS 1.3이 아니라 TLS 1.2로 협상되었다고 믿게 만들 수 있다면, 더 약한 TLS 1.2 환경으로 통신하게 만들 수 있다. TLS 1.2 자체가 항상 깨진다는 뜻은 아니지만, TLS 1.3보다 오래된 알고리즘이나 구조가 남아 있기 때문에 공격 가능성이 커진다.

그래서 TLS 1.3에서는 server가 TLS 1.3을 지원하는데도 불가피하게 TLS 1.2 이하로 협상되는 경우, `ServerHello.Random` 안에 특별한 표시를 넣는다. 이 표시를 **downgrade canary**라고 한다.

`ServerHello.Random`은 총 32 bytes인데, 이 중 앞의 24 bytes는 일반적인 cryptographic random이고, 마지막 8 bytes가 downgrade canary로 사용될 수 있다.

```text
ServerHello.Random = random 24 bytes || downgrade canary 8 bytes
```

만약 TLS 1.3을 지원하는 서버가 TLS 1.2로 협상하게 되면, 마지막 8 bytes에 다음 값이 들어간다.

```text
44 4F 57 4E 47 52 44 01
```

이 값은 ASCII로 보면 `DOWNGRD\x01`이다.

그리고 TLS 1.1 이하로 내려가게 되면 마지막 8 bytes에 다음 값이 들어간다.

```text
44 4F 57 4E 47 52 44 00
```

이건 ASCII로 `DOWNGRD\x00`이다.

여기서 중요한 점은 client가 이 값을 보고 판단할 수 있다는 것이다. client가 TLS 1.3을 지원하고 server도 TLS 1.3을 지원하는 상황이라면, 정상적으로는 TLS 1.3으로 연결되어야 한다. 그런데 결과적으로 TLS 1.2로 협상되었고, server random 마지막에 `DOWNGRD\x01` 같은 값이 보인다면, client는 “서버는 사실 TLS 1.3을 지원하는데 지금 TLS 1.2로 내려왔다”는 사실을 알 수 있다.

즉, 이 값은 서버가 client에게 보내는 경고 신호다.

“나 TLS 1.3 가능한 서버인데 지금 TLS 1.2 이하로 연결되고 있어. 이게 정상적인 협상인지, 중간 공격자가 강제로 낮춘 건지 확인해.”

이런 의미로 보면 된다.

정리하면, TLS 1.3은 호환성을 위해 겉모습을 TLS 1.2처럼 유지한다. 하지만 이 때문에 공격자가 TLS 버전을 낮추는 downgrade attack을 시도할 수 있다. 이를 막기 위해 TLS 1.3 서버는 낮은 버전으로 협상될 때 `ServerHello.Random`의 마지막 8 bytes에 `DOWNGRD` canary 값을 넣는다. client는 이 값을 확인해서 비정상적인 downgrade 가능성을 탐지할 수 있다.

# Session Resumption : ID/Ticket - PSK

먼저 session resumption은 “이전에 한 번 TLS 연결을 맺은 적이 있으니, 다음 연결에서는 처음부터 full handshake를 다시 하지 말고 더 빠르게 연결하자”는 기능이다. TLS에서는 session이 client와 server 사이에서 만들어지는 암호학적 상태이고, 재사용 가능 여부를 나타내는 `is resumable` 같은 개념도 있다.

## TLS 1.2
TLS 1.2에서는 재연결을 빠르게 하기 위한 방식이 크게 두 가지 있었다.

### Session ID
첫 번째는 **Session ID 방식**이다.  
서버가 세션 상태를 자신의 cache에 저장해두고, 그 세션을 식별하기 위한 32-byte Session ID를 client에게 준다. 나중에 client가 다시 접속할 때 이 Session ID를 보내면, server는 cache에서 해당 세션 상태를 찾는다. 아직 남아 있으면 full handshake를 하지 않고 abbreviated handshake로 빠르게 연결할 수 있다.

흐름은 대략 이렇게 보면 된다.

처음 연결:
- server가 session state 저장
- client에게 Session ID 제공

다시 연결:
- client가 Session ID 제시
- server가 cache에서 찾음
- 있으면 1-RTT abbreviated handshake

이 방식의 특징은 **server가 상태를 저장해야 한다**는 점이다. 즉, server cache에 session state가 남아 있어야 재개가 가능하다. 그래서 사용자가 많아지거나 서버가 여러 대로 분산되면, 세션 상태를 공유하거나 관리해야 하는 부담이 생긴다.

### Session Ticket
두 번째는 **Session Ticket 방식**이다.  
이 방식에서는 server가 세션 상태를 직접 cache에 들고 있지 않는다. 대신 server가 session state를 자신의 STK, 즉 session ticket key로 암호화해서 ticket 형태로 client에게 준다. client는 나중에 다시 접속할 때 이 ticket을 server에게 그대로 보낸다. 그러면 server는 ticket을 복호화해서 이전 세션 정보를 복원하고, abbreviated handshake를 진행할 수 있다.

흐름은 이렇게 볼 수 있다.

처음 연결:
- server가 session state를 암호화
- client에게 Session Ticket 제공

다시 연결: 
- client가 Session Ticket 제시
- server가 ticket 복호화
- 복호화 성공하면 1-RTT abbreviated handshake

이 방식의 장점은 **server가 stateless하게 동작할 수 있다**는 점이다. 세션 정보를 서버 메모리에 저장해두는 대신, 암호화된 ticket 자체가 세션 정보를 들고 있기 때문이다. 그래서 대규모 서비스나 로드밸런싱 환경에서는 Session Ticket 방식이 더 유리하다.

이 내용이 나온 이유는, TLS 1.3에서 이 복잡한 구조가 **PSK 기반 resumption**으로 정리되기 때문이다. 여기서 PSK는 Pre-Shared Key인데, 꼭 사람이 미리 정해둔 비밀번호 같은 것만 의미하는 게 아니라, 이전 TLS 연결을 통해 만들어진 secret을 다음 연결에서 재사용하는 방식도 포함한다. 즉, TLS 1.3은 TLS 1.2의 Session ID/Ticket 개념을 더 일반화해서 **PSK로 재개한다**고 보면 된다.

# TLS 1.2 1-RTT  Resumption(Abbreviated Handshake)
앞에서는 Session ID 방식과 Session Ticket 방식을 따로 봤고, 여기서는 그 둘이 실제 handshake에서 어떻게 사용되는지를 정리해보자

TLS 1.2에서 처음 연결할 때는 full handshake를 해야 한다. 이때 client와 server는 master secret, cipher suite, session id 같은 세션 상태를 만든다. 그런데 같은 client가 나중에 다시 접속한다면, 이미 만들어둔 세션 정보를 재사용해서 handshake를 줄일 수 있다. 이게 **session resumption**이고, TLS 1.2에서는 보통 **1-RTT abbreviated handshake**라고 부른다.

![](../images/Pasted%20image%2020260603195943.png)

흐름은 먼저 client가 `ClientHello`를 보내면서 이전에 받은 `session_id`나 `session ticket`을 같이 보낸다. 이 말은 “나 전에 너랑 연결한 적 있는데, 이 세션 다시 쓸 수 있어?”라고 묻는 것과 같다.

그다음 server는 두 가지 중 하나를 한다.

- Session ID 방식: server가 자신의 cache에서 해당 session_id를 찾음
- Session Ticket 방식: client가 보낸 ticket을 server가 복호화해서 세션 정보를 복원함

둘 중 어느 방식이든 server가 이전 세션 상태를 사용할 수 있다고 판단하면, full handshake를 다시 하지 않는다. 그래서 server는 `ServerHello`를 보내고, 바로 `ChangeCipherSpec`, `Finished`를 보낸다. 여기서 `Certificate`, `ServerKeyExchange`, `ServerHelloDone` 같은 과정이 생략된다.

그다음 client도 `ChangeCipherSpec`을 보내고, 암호화된 `[Finished]`를 보낸다. 그리고 바로 `[Application Data]`도 이어서 보낼 수 있다. 그림에서 대괄호 `[ ... ]`로 표시된 부분은 **새로 만들어진 session key로 암호화된 메시지**라는 뜻이다.

여기서 중요한 점은 “이전 세션 키를 그대로 다시 쓰는가?”인데, 정확히는 **이전 세션 상태를 기반으로 새로운 session key를 만든다**고 보는 게 좋다. 즉, 이전 master secret이나 ticket 정보를 재사용하되, 이번 연결에서 사용할 암호화 키는 새로 계산된다. 그래서 그림에서도 `[Finished]`, `[Application Data]`가 **new session keys**로 암호화된다고 표현한 것이다.

TLS 1.2 full handshake와 비교하면 차이가 더 잘 보인다.

![](../images/Pasted%20image%2020260603200052.png)

즉, 재연결에서는 서버 인증서 검증과 키 교환 과정을 다시 길게 하지 않기 때문에 빠르다. 대신 이전에 안전하게 만들어둔 세션 상태를 믿고, 그것을 기반으로 연결을 재개한다.

# Session Resumption : ID/Ticket - PSK

TLS 1.2에서는 재연결 방식이 둘로 나뉘어 있었다.  
하나는 server가 session state를 cache에 저장해두고 client가 `session_id`를 다시 제시하는 방식이고, 다른 하나는 server가 session state를 암호화한 ticket을 client에게 주고 나중에 client가 그 ticket을 다시 가져오는 방식이었다.

TLS 1.3에서는 이 둘을 따로 보지 않고, 전부 **PSK 기반 resumption**으로 정리한다. 여기서 PSK는 Pre-Shared Key인데, 꼭 사람이 미리 정해둔 비밀번호 같은 의미는 아니다. TLS 1.3에서는 이전 handshake를 통해 만들어진 secret을 바탕으로 다음 연결에서 사용할 수 있는 공유 비밀값을 만든다. 즉, “이미 이전 연결에서 안전하게 공유한 값이 있으니, 다음 연결에서는 그 값을 기반으로 빠르게 다시 연결하자”는 구조다.

처음 연결에서는 일반적인 TLS 1.3 full handshake가 진행된다. 이 과정이 끝나면 server는 client에게 `NewSessionTicket`을 보낸다. 이 ticket 안에는 PSK를 식별하기 위한 identity와 필요한 parameter들이 들어 있다. 양쪽은 이때 handshake 과정에서 얻은 값으로부터 `resumption_master_secret`을 만들고, 이것을 바탕으로 나중에 사용할 PSK를 계산할 수 있다.

이후 client가 다시 접속할 때는 `ClientHello`에 `pre_shared_key` extension과 `psk_key_exchange_modes` extension을 넣는다. `pre_shared_key`는 “이전에 받은 이 PSK identity를 사용해서 재연결하고 싶다”는 의미이고, `psk_key_exchange_modes`는 PSK를 어떤 방식으로 쓸 것인지를 알려준다.

TLS 1.3에서 재연결은 크게 두 가지 방식으로 볼 수 있다.

### 1-RTT resumption
첫 번째는 **1-RTT resumption**이다.  
client가 `ClientHello`에 PSK 정보를 넣어 보내면, server는 해당 PSK identity를 확인하고, 이를 기반으로 handshake를 줄인다. 이후 server의 `Finished`, client의 `Finished`가 오가고 연결이 완료된다. TLS 1.2의 abbreviated handshake와 비슷하게, full handshake보다 빠르게 연결을 재개하는 방식이다.

### 0-RTT resumption
두 번째는 **0-RTT resumption**, 즉 early data 방식이다.  
client는 첫 `ClientHello`를 보낼 때 바로 `early_data`를 붙여서 Application Data를 보낼 수 있다. 이 데이터는 PSK에서 파생된 early traffic secret으로 암호화된다. 그래서 server 응답을 기다리기 전에 데이터를 먼저 보낼 수 있다. 다만 0-RTT는 replay attack 문제가 있을 수 있기 때문에, 모든 요청에 안전하게 사용할 수 있는 것은 아니다. 예를 들어 단순 조회 요청처럼 다시 실행되어도 큰 문제가 없는 데이터에는 사용할 수 있지만, 결제나 상태 변경 요청에는 조심해야 한다.

정리하면, TLS 1.3은 TLS 1.2에 있던 Session ID와 Session Ticket이라는 두 재연결 방식을 **PSK라는 하나의 모델로 통합**했다. 처음 연결 후 server가 `NewSessionTicket`을 보내고, 양쪽은 `resumption_master_secret`을 기반으로 PSK를 계산한다. 이후 client는 `pre_shared_key`를 제시해서 1-RTT로 빠르게 재연결하거나, 경우에 따라 0-RTT early data까지 보낼 수 있다. 핵심은 **재연결 구조를 단순화하면서도 더 빠른 연결을 가능하게 만든 것**이다.

# TLS 1.3 1-RTT  Resumption

앞에서 TLS 1.2의 Session ID / Session Ticket이 TLS 1.3에서는 PSK 하나로 정리된다고 했는데, 여기서는 그 PSK를 실제 handshake에서 어떻게 쓰는지를 보자

![](../images/Pasted%20image%2020260603200359.png)

TLS 1.3의 1-RTT resumption은 **이전 연결에서 만들어진 PSK를 기반으로 다시 연결하되, key_share도 함께 사용해서 새 키를 만드는 방식**이다. TLS는 handshake를 통해 client/server 사이의 암호학적 파라미터와 shared secret을 만들고, 이후 record 보호에 필요한 키를 생성하는 구조인데, TLS 1.3 resumption에서는 이전 세션의 secret을 재사용해서 이 과정을 줄인다.

처음에 client는 `ClientHello`를 보낼 때 다음 정보를 같이 넣는다.

```text
ClientHello
+ key_share
+ pre_shared_key
+ psk_key_exchange_modes
```

여기서 `pre_shared_key`는 “나 이전에 받은 PSK identity를 가지고 있으니 이걸로 재연결하고 싶다”는 의미다. `psk_key_exchange_modes`는 PSK를 어떤 방식으로 사용할지 알려주는 필드다. 그리고 `key_share`는 새 ECDHE 키 교환에 필요한 client의 임시 공개값이다.

여기서 중요한 점은 **PSK만 쓰는 게 아니라 key_share도 같이 보낸다**는 것이다. 이렇게 하면 이전 세션에서 파생된 PSK를 사용하면서도, 이번 연결에서 새 ECDHE 값을 섞어 새로운 handshake key를 만들 수 있다. 그래서 단순히 예전 키를 그대로 다시 쓰는 느낌이 아니라, **이전 세션의 신뢰 기반 + 이번 연결의 새 key exchange**를 결합하는 구조라고 보면 된다.

server는 client가 보낸 PSK identity를 확인하고 사용할 수 있으면, `ServerHello`에서 자신의 `key_share`와 선택한 `pre_shared_key` 정보를 보낸다.

```text
ServerHello
+ key_share
+ pre_shared_key
```

이 시점에서 client와 server는 PSK와 ECDHE 결과를 이용해 handshake traffic secret을 계산할 수 있다. 그래서 그 뒤의 `EncryptedExtensions`와 `Finished`는 암호화되어 전달된다.

그림에서 `{ ... }`와 `[ ... ]` 표시가 나뉘어 있는 것도 중요하다.

```text
{ ... } = handshake traffic secret으로 보호
[ ... ] = application traffic secret으로 보호
```

즉, `{ EncryptedExtensions, Finished }`는 아직 handshake를 마무리하는 단계의 키로 보호된다. 반면 `[ Application Data ]`는 handshake가 끝난 뒤 실제 데이터를 보호하는 application traffic secret으로 보호된다.

client도 server의 `Finished`를 받은 뒤 자신의 `{ Finished }`를 보낸다. 그리고 바로 `[ Application Data ]`를 이어서 보낼 수 있다. 이게 1-RTT resumption의 핵심이다. client가 처음 `ClientHello`를 보내고 server의 응답을 한 번 받은 뒤, 바로 자신의 Finished와 실제 데이터를 보낼 수 있기 때문에 빠르다.

결국 이 부분은 TLS 1.3의 재연결이 단순히 “이전 세션을 다시 쓰는 것”이 아니라, **이전 세션에서 얻은 PSK를 사용해 handshake를 줄이고, 동시에 새 key_share를 섞어서 안전하게 새 연결 키를 만드는 방식**이라는 점을 보여준다.

# TLS 1.3 0-RTT Resumption

앞의 1-RTT resumption에서는 client가 `ClientHello`를 보내고, server의 `ServerHello`를 받은 뒤에야 client가 `Finished`와 Application Data를 보낼 수 있었다. 그런데 0-RTT에서는 client가 첫 번째 `ClientHello`를 보낼 때부터 바로 Early Application Data를 같이 보낸다.

![](../images/Pasted%20image%2020260603200421.png)

흐름을 보면 client는 처음에 다음 정보를 같이 보낸다.

```text
ClientHello
+ key_share
+ pre_shared_key
+ psk_key_exchange_modes
+ early_data extension
```

여기서 `pre_shared_key`는 이전 연결에서 얻은 PSK를 사용하겠다는 의미이고, `early_data extension`은 “나는 0-RTT 데이터를 보내겠다”는 표시다. 그리고 바로 아래에 `( Early Application Data )`가 붙어 있다. 이게 핵심이다. client가 server 응답을 받기도 전에 실제 데이터를 먼저 보내는 것이다.

이 Early Application Data는 이전 세션의 PSK에서 파생된 **early traffic secret**으로 암호화된다. 그림에서 `( ... )`가 early traffic secret을 의미한다. 즉, 아직 이번 연결의 ECDHE 결과가 완전히 반영되기 전이기 때문에, 이 구간은 이전 세션의 PSK에 의존한다.

여기서 중요한 한계가 바로 **no PFS**이다. PFS는 Perfect Forward Secrecy인데, 나중에 장기 키나 PSK 관련 정보가 노출되더라도 과거 통신 내용을 보호할 수 있는 성질이다. 그런데 0-RTT Early Data는 이번 연결의 새 ECDHE 결과를 사용하기 전에 보내지기 때문에, PSK 기반으로만 보호된다. 그래서 이 부분은 일반적인 TLS 1.3 handshake 이후 데이터보다 보안성이 약하다.

그다음 server는 `ServerHello + key_share + pre_shared_key`를 보낸다. 이 시점부터는 client와 server가 PSK와 새 ECDHE key share를 함께 사용해서 handshake traffic secret을 만들 수 있다. 그래서 이후 server가 보내는 `{ EncryptedExtensions + early_data, Finished }`는 handshake traffic secret으로 보호된다.

그다음 `[ Application Data ]`는 application traffic secret으로 보호된다. 즉, Early Data와 일반 Application Data는 사용하는 키가 다르다.

```text
( Early Application Data )
→ early traffic secret 사용
→ 이전 PSK 기반
→ no PFS

{ EncryptedExtensions, Finished }
→ handshake traffic secret 사용

[ Application Data ]
→ application traffic secret 사용
→ 새 handshake 이후의 정상 데이터 보호
```

client 쪽 마지막을 보면 `( EndOfEarlyData ), { Finished }, [ Application Data ]`가 이어진다. `EndOfEarlyData`는 client가 “이제 early data 전송은 끝났다”고 알리는 메시지다. 그 후 client는 handshake traffic secret으로 `Finished`를 보내고, 이후부터는 application traffic secret으로 일반 Application Data를 보낸다.

정리하면, TLS 1.3 0-RTT resumption은 **이전 세션의 PSK를 이용해서 첫 패킷부터 데이터를 보낼 수 있게 하는 방식**이다. 그래서 지연 시간은 가장 적다. 하지만 Early Data는 이번 연결의 새 ECDHE 결과가 반영되기 전에 보내지므로 PFS가 없고, replay attack 위험도 있다. 따라서 조회 요청처럼 반하지만 Early Data는 이번 연결의 새복되어도 큰 문제가 없는 데이터에는 적합하지만, 결제, 주문, 계정 변경처럼 한 번만 실행되어야 하는 요청에는 조심해야 한다.

# Other Improvements

먼저 **0-RTT early data**는 session resumption에서 사용하는 기능이다. 이전 연결에서 만들어진 PSK를 가지고 있으면, client는 새 연결에서 server 응답을 기다리지 않고 첫 번째 메시지에 Application Data를 같이 보낼 수 있다. 그래서 지연 시간을 거의 0-RTT 수준으로 줄일 수 있다. 다만 이 early data는 이전 세션의 PSK에서 파생된 키로 보호되기 때문에, 이번 연결의 새로운 ECDHE 결과가 아직 반영되지 않는다. 그래서 **forward secrecy가 없다**는 한계가 있다. 즉, 빠르지만 보안적으로는 일반 Application Data보다 조심해서 써야 한다.

다음은 **HKDF 기반 key scheduling**이다. TLS 1.2에서는 PRF를 사용해서 master secret에서 여러 키를 만들어냈다. TLS 자료에서도 TLS는 handshake를 통해 shared secret을 만들고, 여기서 MAC key, encryption key, IV 같은 key material을 생성한다고 설명한다. TLS 1.3에서는 이 구조를 HKDF로 바꿔서 더 명확하게 정리했다.

TLS 1.3에서는 키가 한 번에 대충 만들어지는 것이 아니라, 단계별로 나뉜다.

```text
early traffic secret
handshake traffic secret
application traffic secret
```

즉, early data를 보호하는 키, handshake 메시지를 보호하는 키, 실제 Application Data를 보호하는 키가 서로 분리된다. 그래서 한 단계의 키가 다른 단계에 직접 영향을 주지 않도록 설계되어 있다. 앞에서 말했던 것처럼 `Finished`와 Application Data가 거의 이어서 전송되더라도, 서로 다른 키를 사용하는 이유도 이 구조 때문이다.

또한 TLS 1.3은 **방향별로도 키를 분리**한다. client가 server로 보내는 데이터용 키와 server가 client로 보내는 데이터용 키가 따로 있다. 그리고 phase별로도 키가 다르다. 그래서 정리하면 다음과 같다.

```text
client handshake traffic key
server handshake traffic key

client application traffic key
server application traffic key
```

이렇게 나누면 한쪽 방향의 키나 특정 단계의 키가 문제가 생겼을 때 다른 방향이나 다른 단계로 영향이 퍼지는 것을 줄일 수 있다. 또한 TLS 1.3은 재협상 없이 key update를 지원할 수 있다. 즉, 연결을 유지한 상태에서 application traffic key를 새로 갱신할 수 있다.

마지막은 **제거되거나 변경된 기능들**이다. TLS 1.3에서는 renegotiation, compression, custom DHE group 같은 기능들이 제거되었다. 이유는 단순히 기능을 줄이기 위해서가 아니라, 과거에 보안 문제를 만들었거나 구현 복잡도를 높였기 때문이다.

`renegotiation`은 기존 연결 중간에 handshake를 다시 하는 기능인데, 복잡하고 공격 표면이 컸다. `compression`은 CRIME 같은 공격과 관련이 있어서 제거되었다. `custom DHE group`은 임의의 약한 그룹을 사용할 위험이 있기 때문에 제거되고, 안전하게 정해진 그룹을 협상하는 방식으로 정리되었다.
